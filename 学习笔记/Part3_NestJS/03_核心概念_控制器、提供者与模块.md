## 一、RESTful 风格设计

### 1.1 先用大白话理解

想象你去一家银行办业务：

- **传统窗口模式**：一排窗口，每个窗口只办一件事——"开卡窗口""存钱窗口""销户窗口"。你想办同一张卡的三件事，得跑三个不同的窗口，告诉柜员"我的卡号是 12345"。
- **RESTful 模式**：只有一个窗口叫"银行卡业务"，你拿着卡号 12345 过去，**做什么由你的动作决定**——递进去一张"查询单"就是查，递进去"存款单"就是存，递进去"注销单"就是销。

对，==RESTful 的核心就是：**用同一个 URL 表示同一个资源，用不同的请求方法来区分你想对它做什么。** URL 只负责"它是谁"，方法负责"干什么"。==

### 1.2 专业定义

**RESTful（Representational State Transfer，表现层状态转移）** 是一种**==接口设计风格==**，不是标准也不是协议——你完全可以不按它写，照样能跑。

它的核心约定是：

> ==一切皆资源（Resource），每个资源有唯一的 URL 标识（URI）；对资源的操作由 HTTP 方法（Method）语义来表达。==

再记住两个术语：

- **资源（Resource）**：==接口操作的对象==，比如"用户""订单""文章"。在 URL 里通常用**名词**表示。
- **端点（Endpoint）**：==一个 URL + 一个方法的组合==，比如 `GET /user` 就是一个端点。

### 1.3 传统接口 vs RESTful 接口

先看**传统写法**（也叫"动宾式 URL"，把**动作写进 URL 里**）：

```
http://localhost:8080/api/get_list?id=1      查询
http://localhost:8080/api/delete_list?id=1   删除
http://localhost:8080/api/update_list?id=1   更新
```

再看 RESTful 写法：

```
http://localhost:8080/api/user/1            查询 / 更新 / 删除 都是这一个 URL
```

区别一目了然：**RESTful 用一个 URL 完成了增删改查，具体操作靠请求方法区分。**

 🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩

| 对比项 | 传统接口 | RESTful 接口 |
| --- | --- | --- |
| URL 里有没有动词 | 有（get_list / delete_list） | 没有，只有名词（user） |
| 动作写在哪 | URL 里 | HTTP 方法里（==GET / POST / PUT / DELETE==） |
| 参数写在哪 | 查询串 `?id=1` | 路径里 `/user/1` |
| 一个资源几个 URL | 3~4 个 | 通常 1 个 |
| 可读性 | 一眼知道干什么，但 URL 越堆越多 | URL 干净，需要看方法才知道干什么 |
| 语义规范性 | 各写各的 | 业界统一，前后端沟通成本低 |

### 1.4 HTTP 方法与方法语义

| 方法 | 语义 | 对应 SQL | 幂等性（重复调用结果一样吗） | 典型 URL |
| --- | --- | --- | --- | --- |
| GET | 查询 | SELECT | 是 | `GET /user`、`GET /user/1` |
| POST | 新增 | INSERT | 否（调两次会建两条） | `POST /user` |
| PUT | ==全量==更新（整体替换） | UPDATE | 是 | `PUT /user/1` |
| PATCH | ==局部==更新（只改传过来的字段） | UPDATE | 是 | `PATCH /user/1` |
| DELETE | 删除 | DELETE | 是 | `DELETE /user/1` |

> 小白最容易踩的点：**PUT 和 PATCH 都叫"更新"，但含义不同。** PUT 是"我把这条记录的完整新版本交给你，你整条覆盖"；PATCH 是"我只改了年龄，你只改年龄，别的字段别动"。

### 1.5 一个完整的 RESTful 控制器

在 NestJS 里，上面的设计就是一个 Controller 里的 6 个方法。假设项目是 01 篇里用 `nest g res user` 生成的：

```ts
// src/user/user.controller.ts
import {
  Controller,
  Get,
  Post,
  Put,
  Patch,
  Delete,
  Body,
  Param,
} from '@nestjs/common';

// 这里先用接口代替 DTO 类，正式项目应放在 dto/ 目录下
interface CreateUserDto {
  name: string;
  age: number;
}

@Controller('user') // 控制器级路由前缀：本类所有接口都以 /user 开头
export class UserController {
  // GET /user —— 查列表
  @Get()
  findAll() {
    return [{ id: 1, name: '小明' }];
  }

  // GET /user/1 —— 查单条（:id 是动态路由参数）
  @Get(':id')
  findOne(@Param('id') id: string) {
    return { id: +id }; // +id 把字符串 "1" 转成数字 1
  }

  // POST /user —— 新增
  @Post()
  create(@Body() dto: CreateUserDto) {
    return { message: '新增成功', data: dto };
  }

  // PUT /user/1 —— 全量更新
  @Put(':id')
  updateAll(@Param('id') id: string, @Body() dto: CreateUserDto) {
    return { id: +id, ...dto };
  }

  // PATCH /user/1 —— 局部更新
  @Patch(':id')
  updatePart(@Param('id') id: string, @Body() dto: Partial<CreateUserDto>) {
    return { id: +id, ...dto };
  }

  // DELETE /user/1 —— 删除
  @Delete(':id')
  remove(@Param('id') id: string) {
    return { message: `已删除 id 为 ${id} 的用户` };
  }
}
```

**验收方式**：`npm run start:dev` 启动后，用 Postman / Apifox 依次请求 `GET http://localhost:3000/user`、`GET http://localhost:3000/user/1` 等，观察返回。==注意同一串 URL 换成不同方法，命中的是不同方法。==

> 补充：DTO
>
> # DTO
>
> 全称：**==Data Transfer Object==，数据传输对象** 一句话：**专门用来==接收前端传过来的参数==，或者==返回给前端数据==的类，只负责数据传输，不包含业务逻辑**
>
> ## 核心作用  🥸🥸🥸🥸🥸🥸🥸
>
> 1. **约束数据结构**：规定接口接收/返回哪些字段、类型、是否必填
> 2. **参数校验**：配合校验库（Nest：class-validator；Spring：@Valid + JSR380），自动校验参数
> 3. **隔离层，保护实体（Entity）** 数据库实体 Entity 是和表一一对应的，里面可能有密码、创建时间、删除标记等敏感字段。 DTO 不和数据库直接绑定，**不要把数据库实体直接丢给前端，也不要直接拿前端参数去映射数据库实体**。
>
> 举个例子： 数据库用户实体 `UserEntity` 字段：id、username、password、phone、createTime、isDelete 前端注册只需要传：username、password、phone 👉 单独写 `CreateUserDto`，只包含这三个字段，不会把密码、删除标记这些乱传。
>
> ## NestJS 里的 DTO（TS）
>
> ```ts
> // create-user.dto.ts
> import { IsString, IsNotEmpty, IsPhoneNumber } from 'class-validator'
> 
> export class CreateUserDto {
>   @IsNotEmpty()
>   @IsString()
>   username: string
> 
>   @IsNotEmpty()
>   @IsString()
>   password: string
> 
>   @IsPhoneNumber('CN')
>   phone: string
> }
> ```
>
> 在 Controller 直接接收：
>
> ```ts
> @Post()
> create(@Body() dto: CreateUserDto) {
>   return this.userService.create(dto);
> }
> ```
>
> ## Spring MVC 里的 DTO（Java）
>
> ```java
> import jakarta.validation.constraints.NotBlank;
> 
> public class CreateUserDTO {
>     @NotBlank(message = "用户名不能为空")
>     private String username;
>     @NotBlank(message = "密码不能为空")
>     private String password;
>     private String phone;
> 
>     // getter、setter
> }
> ```
>
> Controller：
>
> ```java
> @PostMapping("/user")
> public String create(@Valid @RequestBody CreateUserDTO dto){
>     return userService.create(dto);
> }
> ```
>
> ## DTO 容易混淆的几个概念
>
> 1. **DTO：数据传输对象** → 接口和前端之间传数据（入参、出参）
>
> 2. **Entity / PO（Persistent Object 持久化对象）** → 和数据库表一一对应，ORM映射（TypeORM、MyBatis、JPA）
>
> 3. **VO：View Object 视图对象** → 很多公司习惯把**返回给前端**的对象叫VO；接收前端参数的叫DTO。
>
>    > 小提示：很多团队简化，不分VO，入参出参都统一叫DTO。
>
> ## 关键原则
>
> ✅ DTO 只定义字段、校验规则，**不写业务方法** ✅ 一个接口对应一个DTO，新增、修改可以分开（CreateUserDto、UpdateUserDto） ❌ 禁止直接把 Entity 当做接收参数、返回结果的对象
>
> ## 一句话区分
>
> - Entity：面向数据库
> - DTO：面向接口（前后端之间传输）
>
> ==Nest 中：Controller 接收 DTO → 传给 Service → Service 组装成 Entity 去操作数据库。==

### 1.6 URL 设计的三条小规矩

1. **用名词，不用动词**：`/user` 而不是 `/getUser`。动作交给方法。
2. **用复数表示"集合"**：`/user` 查列表、`/user/1` 查具体某条。业界更常见的写法是 `/users`、`/users/1`，两种都能用，本项目沿用原文的 `/user`。
3. **层级别太深**：`/user/1/order` 表示"用户 1 的订单"，可以；`/user/1/order/2/goods/3/comment` 就属于设计失控，应改成 `/comment?goodsId=3`。

### 1.7 ==接口版本控制==

接口上线后不能随便改，否则老版本 App 会崩。所以需要**版本控制**。NestJS 内置支持三种方式：

| 方式 | 英文 | 版本写在哪 | 示例 |
| --- | --- | --- | --- |
| URI 版本控制 | URI Versioning | URL 路径里（**默认方式，最语义化，一般用这个**） | `GET /v1/user` |
| Header 版本控制 | Header Versioning | 自定义请求头里 | `X-Version: 1` |
| Media Type 版本控制 | Media Type Versioning | `Accept` 请求头里 | `Accept: application/json;v=1` |

**第一步：在入口文件开启版本控制**

```ts
// src/main.ts
import { NestFactory } from '@nestjs/core';
import { VersioningType } from '@nestjs/common';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);

  // 开启 URI 版本控制，接口会变成 /v1/xxx、/v2/xxx
  app.enableVersioning({
    type: VersioningType.URI,
    defaultVersion: '1', // 不写版本号的接口默认按 1 版处理
  });

  await app.listen(3000);
}
bootstrap();
```

**第二步：在 Controller 上声明版本**

关键变化：`@Controller()` 的参数从**字符串**变成了**对象**，用 `path` 指定路径、`version` 指定版本。

```ts
// src/user/user.controller.ts
import {
  Controller,
  Get,
  Post,
  Body,
  Patch,
  Param,
  Delete,
  Version,
} from '@nestjs/common';
import { UserService } from './user.service';
import { CreateUserDto } from './dto/create-user.dto';
import { UpdateUserDto } from './dto/update-user.dto';

@Controller({
  path: 'user', // 等价于原来的 @Controller('user')
  version: '1', // 这个控制器整体属于 v1
})
export class UserController {
  constructor(private readonly userService: UserService) {}

  @Post()
  create(@Body() createUserDto: CreateUserDto) {
    return this.userService.create(createUserDto);
  }

  @Get()
  findAll() {
    return this.userService.findAll();
  }

  // 单个接口想指定别的版本，用 @Version() 覆盖类上的版本
  // @Version('2')
  @Get(':id')
  findOne(@Param('id') id: string) {
    return this.userService.findOne(+id);
  }

  @Patch(':id')
  update(@Param('id') id: string, @Body() updateUserDto: UpdateUserDto) {
    return this.userService.update(+id, updateUserDto);
  }
}
```

此时接口地址变成 `http://localhost:3000/v1/user`。想验证版本确实生效，把 `version: '1'` 改成 `'2'`，再请求 `/v1/user` 会得到 404，请求 `/v2/user` 才有响应。

### 1.8 状态码（Code）规范

HTTP 状态码是接口的"体检报告"，前端靠它判断这次请求是成功、参数错了还是服务器炸了。

| 状态码 | 名称 | 什么时候用 |
| --- | --- | --- |
| 200 | OK | 请求成功，正常返回数据（默认） |
| 304 | Not Modified | 协商缓存命中，内容没变，让浏览器用本地缓存 |
| 400 | Bad Request | 参数错误（少传、类型不对、校验不通过） |
| 401 | Unauthorized | 未登录 / token 错误或过期 |
| 403 | Forbidden | 身份认了但没权限（常因 referer / origin 校验失败） |
| 404 | Not Found | 接口不存在，或资源不存在 |
| 500 | Internal Server Error | 服务端代码报错（未捕获异常） |
| 502 | Bad Gateway | 上游接口有问题或服务器挂了（网关转发失败） |

> 小白对照记法：**4 开头是我的问题（客户端），5 开头是它的问题（服务端）。**

怎么在 NestJS 里改状态码？用 `@HttpCode()` 装饰器，详见 2.7 节。

### 1.9 常见错误与排查

**问题 1：所有接口都返回 404，连 `/user` 都打不通**

- 原因 A：Controller 没在对应 Module 的 `controllers` 数组里注册，Nest 根本没加载它。
- 原因 B：开了版本控制，但请求 URL 里没带 `/v1`。
- 解决：检查 `xxx.module.ts` 的 `controllers: [UserController]`；再确认访问地址是否带了版本前缀。

**问题 2：`GET /user/1` 和 `GET /user` 混淆，访问 `/user/1` 却进了 `findAll`**

- 原因：路由匹配按声明顺序进行，若 `@Get(':id')` 写在 `@Get()` 之前，`/user` 也可能被 `:id` 吃掉。
- 解决：把**更具体**的路由（`@Get()`）写在**更宽泛**的（`@Get(':id')`）前面。

**问题 3：`@Param('id') id` 拿到的 `"1"` 是字符串，和数字比较永远不相等**

- 原因：URL 里的所有片段天然是字符串。
- 解决：用 `+id`、`Number(id)` 或 `parseInt(id, 10)` 显式转数字。

## 二、控制器 Controller 与参数装饰器

### 2.1 先用大白话理解

Controller 就是**公司前台**。

前台不负责做事，只负责：**接待（接住请求）→ 问清来意（取参数）→ 转给对应部门（调用 Service）→ 把结果回给客人（返回响应）**。

所以一个健康的分工纪律是：==**控制器里只做"取参数 + 调方法 + 返回"，业务逻辑一律放 Service。**== 前台要是自己跑去修电脑，这家公司就乱了。

02 篇已经说过装饰器原理，本篇讲**怎么用**。

### 2.2 参数装饰器总表

NestJS 提供了一批**方法参数装饰器（Method Parameter Decorator）**，直接写在方法的参数前面，就能把请求里的某一部分"抠"出来，不用再写 `req.xxx`。

🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩🍋‍🟩

| 装饰器 | 等价于 Express 原生写法 | 作用 |
| --- | --- | --- |
| `@Request()` / `@Req()` | `req` | 拿到完整请求对象 |
| `@Response()` / `@Res()` | `res` | 拿到完整响应对象 |
| `@Next()` | `next` | 拿到 next 函数 |
| `@Session()` | `req.session` | 拿到 session 对象 |
| `@Param(key?)` | `req.params` / `req.params[key]` | 拿动态路由参数 |
| `@Body(key?)` | `req.body` / `req.body[key]` | 拿请求体（POST/PUT/PATCH） |
| `@Query(key?)` | `req.query` / `req.query[key]` | 拿 URL 查询串参数 |
| `@Headers(name?)` | `req.headers` / `req.headers[name]` | 拿请求头 |
| `@Ip()` | `req.ip` | 拿客户端 IP |
| `@HttpCode(code)` | — | **设置**响应状态码（不是取参数） |

规律很好记：**不带参数名 → 拿整个对象；带参数名（字符串）→ 只拿那一个值。**

### 2.3 获取 GET 请求参数：`@Query()`

GET 请求的参数在 URL 的问号后面：`/user?name=xiaoman&age=18`。

**方式 A：用 `@Request()` 拿原始对象（Express 老写法）**

```ts
// src/user/user.controller.ts
import { Controller, Get, Request } from '@nestjs/common';

@Controller('user')
export class UserController {
  @Get()
  find(@Request() req) {
    console.log(req.query); // { name: 'xiaoman', age: '18' }
    return { code: 200 };
  }
}
```

**方式 B：用 `@Query()` 直接拿（推荐，更简洁）**

```ts
import { Controller, Get, Query } from '@nestjs/common';

@Controller('user')
export class UserController {
  // 拿全部查询参数
  @Get()
  find(@Query() query) {
    console.log(query); // { name: 'xiaoman', age: '18' }
    return { code: 200, data: query };
  }

  // 只拿一个字段，等价于 query.name
  @Get('detail')
  detail(@Query('name') name: string) {
    console.log(name); // 'xiaoman'
    return { code: 200, name };
  }
}
```

两种写法效果完全一样，`@Query()` 只是语法糖。**新手建议直接用 `@Query()`**，代码更短、语义更清楚。

### 2.4 获取 POST 请求体：`@Body()`

POST 的数据放在**请求体（Body）**里，不在 URL 上。用 Apifox 调试时记得选 `Body → JSON`。

```ts
import { Controller, Post, Body, Request } from '@nestjs/common';

@Controller('user')
export class UserController {
  // 方式 A：原始对象
  @Post('raw')
  createRaw(@Request() req) {
    console.log(req.body); // { name: 'xiaoman', age: 18 }
    return { code: 200 };
  }

  // 方式 B：@Body() 拿整个请求体（推荐）
  @Post()
  create(@Body() body) {
    console.log(body); // { name: 'xiaoman', age: 18 }
    return { code: 200 };
  }

  // 方式 C：只拿某一个字段，等价于 body.name
  @Post('one')
  createOne(@Body('name') name: string) {
    console.log(name); // 'xiaoman'
    return { code: 200, name };
  }
}
```

> 注意：`@Body()` 能拿到数据的前提是请求头里带了 `Content-Type: application/json`。如果忘了，`body` 会是空对象 `{}`——这是新手排查 Body 拿不到数据的第一嫌疑点。

### 2.5 动态路由：`@Param()`

动态路由就是 URL 里带冒号的那一段，比如 `@Get(':id')` 里的 `:id`，它是个"变量"，请求什么值就填什么值。

```ts
import { Controller, Get, Param, Request } from '@nestjs/common';

@Controller('user')
export class UserController {
  // 方式 A：原始对象
  @Get('raw/:id')
  findRaw(@Request() req) {
    console.log(req.params); // { id: '1' }
    return { code: 200 };
  }

  // 方式 B：@Param() 拿全部动态参数
  @Get(':id')
  findId(@Param() param) {
    console.log(param); // { id: '1' }
    return { code: 200, id: param.id };
  }

  // 方式 C：只拿某一个，等价于 param.id（最常用）
  @Get(':id/detail')
  findDetail(@Param('id') id: string) {
    return { code: 200, id: +id };
  }
}
```

多个动态参数也一样：`@Get(':userId/order/:orderId')` 配合 `@Param('userId')`、`@Param('orderId')`。

### 2.6 读取请求头：`@Headers()`

请求头里通常放 token、cookie、客户端信息。调试时可以在 Apifox 的 `Headers` 里随便加一个 `Cookie` 试试。

```ts
import { Controller, Get, Headers } from '@nestjs/common';

@Controller('user')
export class UserController {
  // 拿全部请求头
  @Get('headers')
  allHeaders(@Headers() header) {
    console.log(header); // { host: ..., cookie: ..., 'user-agent': ... }
    return { code: 200 };
  }

  // 只拿某一个请求头（注意名字要小写）
  @Get('cookie')
  oneHeader(@Headers('cookie') cookie: string) {
    console.log(cookie); // 'token=abc123'
    return { code: 200, cookie };
  }
}
```

**和响应头区分开**：读请求头用 `@Headers`（复数），**设置**响应头用 `@Header()`（单数，两个参数）：

```ts
import { Controller, Get, Header } from '@nestjs/common';

@Controller('user')
export class UserController {
  // 给响应加一个 Cache-Control 头
  @Header('Cache-Control', 'none')
  @Get('cache')
  noCache() {
    return { code: 200 };
  }
}
```

### 2.7 自定义状态码：`@HttpCode()`

默认情况下：GET 返回 200，POST 返回 201。想改就用 `@HttpCode()`。

```ts
import { Controller, Get, HttpCode, Headers } from '@nestjs/common';

@Controller('user')
export class UserController {
  @Get(':id')
  @HttpCode(500) // 强制这个接口返回 500
  findId(@Headers() header) {
    return { code: 500 };
  }
}
```

> 提醒：`@HttpCode()` 只是"指定 HTTP 状态码"，**不会**让响应体里的 `code` 字段跟着变。上面返回 `{ code: 500 }` 是我们自己手写的，两者没有联动关系。正式项目里通常配合异常过滤器（第 12 章之后的内容）来统一管理状态码。

### 2.8 `@Request` / `@Response` 的两个大坑

`@Request()` 很安全，就是拿到原始 `req`。但 `@Response()` 有坑：

```ts
import { Controller, Get, Res, Response } from '@nestjs/common';

@Controller('user')
export class UserController {
  // 危险写法：注入 @Response() 后，必须自己 res.send()
  @Get('raw-res')
  rawRes(@Response() res) {
    res.send({ code: 200 }); // 不写这句，请求会一直挂着直到超时
    // 而且 return 的返回值会被忽略！
  }
}
```

**坑点说明**：

当你在方法参数里注入 `@Response()`（或 `@Res()`），NestJS 会认为"你要自己接管响应"，于是**不再处理方法的返回值**。

| 写法 | 谁来返回响应 | 后果 |
| --- | --- | --- |
| 不注入 `@Response()`，直接 `return data` | NestJS | 自动序列化成 JSON 并发送，推荐 |
| 注入 `@Response()`，且调用了 `res.send()` | 你自己 | 正常 |
| 注入 `@Response()`，但只 `return data` | 没人 | **请求一直转圈，最终超时** |

**结论：除非你要用 `res.sendFile()`、`res.cookie()` 这类 Express 原生能力，否则不要注入 `@Response()`。**

### 2.9 常见错误与排查

**报错 1：`Nest can't resolve dependencies of the UserController (?). Please make sure that the argument UserService at index [0] is available in the UserModule context.`**

- 原因：Controller 构造器里注入了 `UserService`，但 `UserModule` 的 `providers` 里没登记它。
- 解决：把 `UserService` 加进同模块的 `providers` 数组（详见第三章）。

**现象 2：`@Body()` 拿到 `{}`，`@Query()` 拿到 `{}`**

- 原因：POST 时没带 `Content-Type: application/json`；或调试工具里 Body 类型选成了 `form-data` / `none`。
- 解决：Apifox / Postman 里把 Body 类型切成 `JSON`。

**现象 3：`@Param('id')` 拿到 `undefined`**

- 原因 A：路由写的是 `@Get(':id')`，但请求地址少了这一段，比如只请求了 `/user`。
- 原因 B：名称写错，`@Param('userId')` 但路由是 `:id`。
- 解决：参数名必须和路由里的 `:xxx` 完全一致。

**现象 4：接口一直 pending，浏览器转圈后超时**

- 原因：注入了 `@Response()` 但忘了 `res.send()`。
- 解决：见 2.8 节，去掉 `@Response()` 参数，直接 `return`。

## 三、提供者 Provider 与自定义注入

### 3.1 先用大白话理解

Provider 就是**公司的各个业务部门**。

前台（Controller）只负责接待，真正干活的是部门。但前台不能自己"私自招人"，它得向公司（Nest 的 IoC 容器）要人——这就是"注入"。而公司要能派人，前提是这家公司**在员工名册里登记了这个人**——==名册就是 Module 的 `providers` 数组。==

所以 Provider 的本质是：**一个"可被注入"的东西。** 它可以是一个 Service、一个 Repository、一个工厂函数，甚至就是一个普通字符串或数组。



### 3.2 专业定义 ⭐⭐⭐⭐⭐⭐⭐⭐⭐⭐

> **Provider（提供者）** 是 Nest 的基本概念。Service、Repository、Factory、Helper 等类都可以被视为 Provider，它们都能通过 `constructor` 注入依赖。==Provider 本质上就是**一个用 `@Injectable()` 装饰器标注的类**。==

关键词是 `@Injectable()`（可注入的）：

==在service中定义所有可以提供的服务==

```ts
// src/user/user.service.ts
import { Injectable } from '@nestjs/common';

@Injectable() // 声明"我可以被注入"      1.🥸🥸🥸🥸🥸🥸🥸  
export class UserService {   
  findAll() {
    return [{ id: 1, name: '小明' }];
  }
}
```

02 篇已经讲过"为什么 NestJS 只支持构造器注入"和"忘了 `@Injectable()` 会怎样"，这里不重复，本节重点讲 **Provider 的四种注册写法**。

### 3.3 基本用法（语法糖写法）

==在module中把所有服务登记在注册表`providers`中（数组）==

最常用的写法——直接把类丢进 `providers`：

```ts
// src/user/user.module.ts
import { Module } from '@nestjs/common';
import { UserService } from './user.service';
import { UserController } from './user.controller';

@Module({
  controllers: [UserController],
  providers: [UserService], // 语法糖：Nest 自动 new UserService() 并登记  2🥸🥸🥸🥸🥸🥸🥸
})
export class UserModule {}
```

==在controller中注入==

Controller 里直接按**类型**注入即可：

```ts
// src/user/user.controller.ts
import { Controller, Get } from '@nestjs/common';
import { UserService } from './user.service';

@Controller('user')
export class UserController {
  // 构造器注入：Nest 会自动把 UserService 的实例塞进来  3.🥸🥸🥸🥸🥸🥸🥸 
  constructor(private readonly userService: UserService) {}

  @Get()
  findAll() {
    return this.userService.findAll();
  }
}
```

==**NestJS 只支持**构造器注入==  DI

**关键认知**：`providers: [UserService]` 只是一句**语法糖**，它的完整写法是：

```ts
providers: [
  {
    provide: UserService,   // 令牌（Token）：别人按什么名字来找
    useClass: UserService,  // 实现：实际 new 哪个类
  },
]
```

理解这一点，后面三种写法就通了——**Provider 永远由「令牌 provide」+「怎么产生值 useXxx」两部分组成。**

### 3.4 写法一：`useClass` —— 给同一个类起个别名

把 `provide` 换成自定义的字符串，就等于让这个 Service 有了一个"别名"：

```ts
// src/user/user.module.ts
import { Module } from '@nestjs/common';
import { UserService } from './user.service';
import { UserController } from './user.controller';

@Module({
  controllers: [UserController],
  providers: [
    {
      provide: 'Xiaoman', // 令牌改成一个字符串
      useClass: UserService, // 实际还是 new UserService
    },
  ],
})
export class UserModule {}
```

**此时 Controller 必须用 `@Inject()` 按这个字符串去取**，否则找不到：

```ts
// src/user/user.controller.ts
import { Controller, Get, Inject } from '@nestjs/common';
import { UserService } from './user.service';

@Controller('user')
export class UserController {
  // 令牌是字符串 'Xiaoman'，必须用 @Inject('Xiaoman')
  constructor(
    @Inject('Xiaoman') private readonly userService: UserService,
  ) {}

  @Get()
  findAll() {
    return this.userService.findAll();
  }
}
```

`useClass` 还有一个实用场景：**同一个类注册两份，走不同配置**（这里先记住机制，配置注入在后面章节展开）。

### 3.5 写法二：`useValue` —— 直接注入一个现成的值

`useValue` 不 new 任何东西，直接把一个**现成的值**塞进容器。适合注入配置对象、常量、第三方库实例、测试用的 Mock。

```ts
// src/user/user.module.ts
import { Module } from '@nestjs/common';
import { UserService } from './user.service';
import { UserController } from './user.controller';

@Module({
  controllers: [UserController],
  providers: [
    {
      provide: 'Xiaoman',
      useClass: UserService, // 一个别名 Service
    },
    {
      provide: 'JD',
      useValue: ['TB', 'PDD', 'JD'], // 直接给一个数组
    },
  ],
})
export class UserModule {}
```

Controller 里按令牌取：

```ts
// src/user/user.controller.ts
import { Controller, Get, Inject } from '@nestjs/common';
import { UserService } from './user.service';

@Controller('user')
export class UserController {
  constructor(
    @Inject('Xiaoman') private readonly userService: UserService,
    @Inject('JD') private readonly shops: string[], // 注入数组
  ) {}

  @Get()
  findAll() {
    return {
      list: this.userService.findAll(),
      shops: this.shops, // ['TB', 'PDD', 'JD']
    };
  }
}
```

> 这就是"配置注入"的雏形：把 `baseUrl`、`apiKey` 这类值用 `useValue` 注册成 Provider，任何地方 `@Inject('CONFIG')` 就能用，不用到处写死。

### 3.6 写法三：`useFactory` —— 由工厂函数决定怎么造

当要注入的东西**不能简单 new 出来**（比如需要先算一下、需要依赖别的 Provider、需要异步拿数据），就用工厂函数。

先补两个配合用的服务（素材里用到 `UserService2`、`UserService3`）：

```ts
// src/user/user.service2.ts
import { Injectable } from '@nestjs/common';

@Injectable()
export class UserService2 {
  getName() {
    return '我是 UserService2';
  }
}
```

```ts
// src/user/user.service3.ts
// 注意：UserService3 是在工厂函数里手动 new 的，不需要 @Injectable()
export class UserService3 {
  constructor(private readonly service2: UserService2) {}

  getInfo() {
    return `UserService3 依赖着 ${this.service2.getName()}`;
  }
}
```

注册工厂 Provider，用 `inject` 声明"我这个工厂需要谁"：

```ts
// src/user/user.module.ts
import { Module } from '@nestjs/common';
import { UserService } from './user.service';
import { UserService2 } from './user.service2';
import { UserService3 } from './user.service3';
import { UserController } from './user.controller';

@Module({
  controllers: [UserController],
  providers: [
    {
      provide: 'Xiaoman',
      useClass: UserService,
    },
    {
      provide: 'JD',
      useValue: ['TB', 'PDD', 'JD'],
    },
    UserService2, // 先登记，下面的工厂才能 inject 到它
    {
      provide: 'Test', // 令牌叫 'Test'
      inject: [UserService2], // 声明工厂函数的入参从容器里取谁
      useFactory(UserService2: UserService2) {
        // 工厂函数的返回值，就是这个 Provider 提供的值
        return new UserService3(UserService2);
      },
    },
  ],
})
export class UserModule {}
```

使用：

```ts
// src/user/user.controller.ts
import { Controller, Get, Inject } from '@nestjs/common';
import { UserService3 } from './user.service3';

@Controller('user')
export class UserController {
  constructor(
    @Inject('Test') private readonly testService: UserService3,
  ) {}

  @Get('factory')
  factory() {
    return { info: this.testService.getInfo() };
  }
}
```

> `inject` 数组的顺序，必须和 `useFactory` 函数的形参顺序**一一对应**。写反了就会拿到错的实例，且不报错——很难查。

### 3.7 写法四：`useFactory` 异步版 —— 等结果出来再启动

如果工厂里要做异步操作（读远程配置、连数据库、读文件），可以让 `useFactory` 返回一个 Promise。NestJS 会**等 Promise resolve 完再完成应用启动**。

```ts
// src/user/user.module.ts（节选 providers 数组）
{
  provide: 'sync',
  async useFactory() {
    // 模拟一个耗时 3 秒的异步任务
    return await new Promise((resolve) => {
      setTimeout(() => {
        resolve('sync');
      }, 3000);
    });
  },
}
```

```ts
// src/user/user.controller.ts（节选）
@Controller('user')
export class UserController {
  constructor(@Inject('sync') private readonly syncValue: string) {}

  @Get('sync')
  sync() {
    return { value: this.syncValue }; // 'sync'
  }
}
```

**观察现象**：`npm run start:dev` 启动时会明显卡 3 秒左右才打印 `Nest application successfully started`——因为 Nest 在等这个 Provider 造出来。这就是"异步 Provider 阻塞启动"的效果，也是它被用来做"启动前必须先连上数据库"的原因。

### 3.8 四种写法对比

| 写法 | 令牌（provide） | 值从哪来 | 需要 `@Inject` 吗 | 典型场景 |
| --- | --- | --- | --- | --- |
| 语法糖 `[UserService]` | 类本身 | Nest 自动 `new` 该类 | 不需要，按类型注入 | 90% 的普通 Service |
| `useClass` | 自定义字符串或类 | Nest `new` 指定的类 | 令牌是字符串时需要 | 给同一实现起别名、按环境切换实现 |
| `useValue` | 自定义 | 直接给一个现成值（对象 / 数组 / 字符串） | 需要 | 配置项、常量、Mock |
| `useFactory` | 自定义 | 工厂函数 `return` 的值，可为 Promise | 需要 | 需要依赖其他 Provider、需要异步 |
| `useExisting` | 自定义 | 指向已有的 Provider，**共用同一个实例** | 需要 | 只想起别名、不想重复创建实例 |

> 补充：`useExisting` 素材里没展开，它和 `useClass` 的区别是——`useClass` 会**新建**一个实例，`useExisting` 是**复用**已有实例。知道有这个写法即可，遇到再说。

### 3.9 常见错误与排查

**报错 1：`Nest can't resolve dependencies of the UserController (?, ?). Please make sure that the argument at index [0] is available in the UserModule context.`**

- 原因：用了自定义令牌，但 Controller 里还是按类型注入，或者 `@Inject()` 里的字符串写错了（大小写不一致也算错）。
- 解决：检查 `provide: 'Xiaoman'` 和 `@Inject('Xiaoman')` 是否**完全一致**。

**报错 2：`Nest can't resolve dependencies of the UserController (?). Please make sure that the argument "Xiaoman" at index [0] is available in the UserModule context.`**

- 原因：Controller 里写了 `@Inject('Xiaoman')`，但 `providers` 里没有 `provide: 'Xiaoman'` 这一项。
- 解决：两处配对检查，令牌必须成对出现。

**报错 3：`Nest can't resolve dependencies of the "Test" (?). Please make sure that the argument UserService2 at index [0] is available in the UserModule context.`**

- 原因：`useFactory` 的 `inject: [UserService2]` 里写了 `UserService2`，但 `providers` 数组里没有登记 `UserService2`。
- 解决：`inject` 里的每一项，都必须先在同一个模块的 `providers` 里存在（或从别的模块 `imports` 进来）。

**现象 4：工厂注入拿到的对象"不对劲"，方法报 undefined**

- 原因：`inject: [A, B]` 的顺序和 `useFactory(a, b)` 的形参顺序不一致。
- 解决：顺序严格对齐。

**现象 5：`useValue` 注入后是 `undefined`**

- 原因：`provide` 的令牌和 `@Inject()` 的令牌不是同一个值（字符串 vs 类常量混用）。
- 解决：建议把令牌抽成常量，比如 `export const JD_LIST = 'JD'`，两边都引用这个常量，杜绝手写错。

## 四、模块 Module：共享模块与动态模块

### 4.1 先用大白话理解

Module 就是**组织架构图上的一个部门**。

- 每个部门有自己的员工（`providers`）和对外窗口（`controllers`）。
- 部门可以**借用**其他部门的资源，前提是**在申请单上写明**（`imports`）。
- 部门也可以**对外授权**自己的资源（`exports`），不授权的东西外边一律用不了——这是 Nest 的"边界保护"。
- 公司至少有一个"总部"（根模块 `AppModule`），总部下面挂各部门。

==**为什么要分模块？** 因为小项目可以只用一个模块，但项目一大，所有 Service 堆在一个模块里，谁依赖谁根本看不清。分模块 = 划清边界，让代码有"可拆卸"的单元。==

### 4.2 `@Module()` 的四个属性

| 属性 | 英文 | 放什么 | 类比 |
| --- | --- | --- | --- |
| `controllers` | 控制器 | 本模块的 Controller | 部门对外的窗口 |
| `providers` | 提供者 | 本模块的 Service | 部门内部员工 |
| `imports` | 导入 | 本模块要用到的**其他模块** | 向别的部门借人的申请单 |
| `exports` | 导出 | 本模块愿意**借给别人**的 Provider | 对外授权名单 |

一句话记住：**imports 是"我要用别人的"，exports 是"别人可以用我的"，providers 是"我自己的人"。**

### 4.3 基本用法

用 `nest g res user` 生成 CRUD 模板时，==NestJS **会自动**把 Controller 和 Service 注册进模块==，不用你手写：

```ts
// src/user/user.module.ts（生成后的样子）
import { Module } from '@nestjs/common';
import { UserService } from './user.service';
import { UserController } from './user.controller';

@Module({
  controllers: [UserController], // 自动加进来了
  providers: [UserService], // 自动加进来了
})
export class UserModule {}
```

而 `AppModule` 里也已经自动 `imports` 了 `UserModule`：

```ts
// src/app.module.ts
import { Module } from '@nestjs/common';
import { UserModule } from './user/user.module';

@Module({
  imports: [UserModule], // 总部挂上用户部门
})
export class AppModule {}
```

### 4.4 共享模块（Shared Module）

**需求**：`user` 模块的 `UserService` 想给 `list` 模块用。

**第一步：在 user 模块里 `exports` 出去**

```ts
// src/user/user.module.ts
import { Module } from '@nestjs/common';
import { UserService } from './user.service';
import { UserController } from './user.controller';

@Module({
  controllers: [UserController],
  providers: [UserService],
  exports: [UserService], // 授权：允许别的模块用 UserService
})
export class UserModule {}
```

**第二步：list 模块 `imports` 进来，然后才能注入**

```ts
// src/list/list.module.ts
import { Module } from '@nestjs/common';
import { UserModule } from '../user/user.module';
import { ListService } from './list.service';
import { ListController } from './list.controller';

@Module({
  imports: [UserModule], // 借人：必须先导入 user 模块
  controllers: [ListController],
  providers: [ListService],
})
export class ListModule {}
```

**第三步：在 list 的 Service 里正常注入**

```ts
// src/list/list.service.ts
import { Injectable } from '@nestjs/common';
import { UserService } from '../user/user.service';

@Injectable()
export class ListService {
  constructor(private readonly userService: UserService) {}

  getList() {
    return this.userService.findAll(); // 借来的能力，直接调
  }
}
```

> **一个极容易误解的点**：`exports` 只代表"user 模块**愿意**借"，不代表"list 模块**自动**拿到"。借的一方**必须**在自己的 `imports` 里写 `UserModule`。少写这一步，报错就是那句熟悉的 `Nest can't resolve dependencies of the ListService (?). Please make sure that the argument UserService at index [0] is available in the ListModule context.`

### 4.5 全局模块（Global Module）

如果我们有十几个模块都要用 `UserService`，每个都写一遍 `imports` 太麻烦。可以用 `@Global()` 把它变成全局模块——**一次注册，处处可用，无需 imports**。

```ts
// src/user/user.module.ts
import { Module, Global } from '@nestjs/common';
import { UserService } from './user.service';
import { UserController } from './user.controller';

@Global() // 声明为全局模块
@Module({
  controllers: [UserController],
  providers: [UserService],
  exports: [UserService], // 全局模块也必须 exports，否则依然用不了
})
export class UserModule {}
```

此时 `list` 模块**不用改 `imports`**，直接注入就能用：

```ts
// src/list/list.service.ts —— 不需要 imports: [UserModule]
import { Injectable } from '@nestjs/common';
import { UserService } from '../user/user.service';

@Injectable()
export class ListService {
  constructor(private readonly userService: UserService) {} // 直接可用

  getList() {
    return this.userService.findAll();
  }
}
```

**`@Global()` 使用原则**：

| 建议 | 说明 |
| --- | --- |
| 只给"真正处处要用"的模块加 | 比如配置模块 `ConfigModule`、数据库模块 `DatabaseModule` |
| 别滥用 | 业务模块加了全局，依赖关系就变得隐式，看不出谁用了谁，后期维护痛苦 |
| 仍然要 `exports` | `@Global()` 只是免除 `imports` 的动作，不改变导出规则 |
| 通常只注册一次 | 一般在 `AppModule` 里导入一次即可 |

### 4.6 动态模块（Dynamic Module）

**为什么需要它？** 普通模块在写代码时就已经"定型"了。但有些模块需要**在使用时传参数**才能工作，比如配置模块需要知道配置文件的路径。

**动态模块的本质**：给模块类加一个**静态方法**（约定叫 `forRoot` 或 `register`），这个方法**接收参数**，返回一个 `DynamicModule` 对象（就是 `@Module()` 里那份配置，但可以按参数动态生成）。

完整可运行示例：

```ts
// src/config/config.module.ts
import { Module, DynamicModule, Global } from '@nestjs/common';

// 参数的类型定义
interface Options {
  path: string;
}

@Global() // 配置模块通常做成全局的
@Module({}) // 空的：真正的 providers 在 forRoot 里动态生成
export class ConfigModule {
  // 静态方法：接收参数，返回动态模块配置
  static forRoot(options: Options): DynamicModule {
    // 把要提供的值准备好（这里把路径拼到 /api 后面）
    const configProvider = {
      provide: 'Config',
      useValue: { baseApi: '/api' + options.path },
    };

    return {
      module: ConfigModule, // 必填：标明这是哪个模块的动态版本
      providers: [configProvider],
      exports: [configProvider], // 想给别人用就导出
    };
  }
}
```

**使用方式**：在 `AppModule` 的 `imports` 里**调用静态方法**，把参数传进去。

```ts
// src/app.module.ts
import { Module } from '@nestjs/common';
import { ConfigModule } from './config/config.module';
import { UserModule } from './user/user.module';

@Module({
  imports: [
    ConfigModule.forRoot({ path: '/shop' }), // 传入参数 path = '/shop'
    UserModule,
  ],
})
export class AppModule {}
```

**使用注入的值**：

```ts
// src/user/user.controller.ts
import { Controller, Get, Inject } from '@nestjs/common';

@Controller('user')
export class UserController {
  constructor(
    @Inject('Config') private readonly config: { baseApi: string },
  ) {}

  @Get('config')
  getConfig() {
    return this.config; // { baseApi: '/api/shop' }
  }
}
```

**运行效果**：请求 `GET /user/config` 会返回 `{ "baseApi": "/api/shop" }`——路径中的 `/shop` 正是我们在 `forRoot` 里传进去的。改传 `{ path: '/blog' }`，返回值就变成 `/api/blog`。**同一份模块代码，靠参数产出不同配置，这就是动态模块的价值。**

**`forRoot` vs `register`（命名惯例）**：

| 方法名 | 惯例用途 |
| --- | --- |
| `forRoot(options)` | 全局只注册一次的根配置（如数据库连接、全局配置） |
| `forRootAsync(options)` | 同上，但配置需要异步获取（如从环境变量、远程配置中心） |
| `register(options)` | 需要注册**多份**、每份配置不同的模块（如多数据源） |

这些只是**社区约定**，不影响功能，但跟着约定写别人一看就懂。

### 4.7 常见错误与排查

**报错 1：`Nest can't resolve dependencies of the ListService (?). Please make sure that the argument UserService at index [0] is available in the ListModule context.`**

- 原因 A：`UserModule` 里没 `exports: [UserService]`。
- 原因 B：`ListModule` 里没 `imports: [UserModule]`。
- 解决：**exports 和 imports 必须成对**，缺一个都报这个错。

**报错 2：`A module cannot import itself` 或循环依赖报错 `Index module and User module depend on each other`**

- 原因：`UserModule` imports `ListModule`，同时 `ListModule` 又 imports `UserModule`，形成环。
- 解决 A：把公共的 Service 抽成一个独立的 `SharedModule`，两边都 imports 它。
- 解决 B：用 `forwardRef(() => XxxModule)` 打破循环（进阶用法，遇到再查）。

**报错 3：加了 `@Global()` 还是 `Nest can't resolve dependencies`**

- 原因：全局模块没写 `exports`，或者全局模块本身没被任何模块 `imports`（`@Global()` 的模块必须**至少被根模块导入一次**才生效）。
- 解决：补 `exports`，并确认 `AppModule` 里 `imports` 了它。

**报错 4：`ConfigModule.forRoot` 返回值注入不到，拿到的 `Config` 是 `undefined`**

- 原因：`forRoot` 返回的 `DynamicModule` 里 `providers` 和 `exports` 用了**两个不同的对象实例**（对象字面量写了两次），Nest 会认为是两个令牌。
- 解决：像示例那样**先把 provider 对象存进变量**，`providers` 和 `exports` 引用同一个变量。

## 五、本篇小结

| 要点 | 一句话说明 |
| --- | --- |
| RESTful | 用名词做 URL、用 HTTP 方法表达动作；一个资源一个 URL |
| 方法语义 | GET 查、POST 增、PUT 全量改、PATCH 局部改、DELETE 删 |
| 版本控制 | `app.enableVersioning({ type: VersioningType.URI })` + `@Controller({ path, version })`；单接口可用 `@Version()` 覆盖 |
| 状态码 | 200 成功 / 304 缓存 / 400 参数错 / 401 未登录 / 403 无权限 / 404 找不到 / 500 服务端错 / 502 上游挂 |
| Controller | 只做"接请求 → 取参数 → 调 Service → 返回"，不写业务逻辑 |
| 参数装饰器 | `@Query` 查参数、`@Body` 请求体、`@Param` 动态路由、`@Headers` 请求头；不带名字拿整个对象，带名字拿单个值 |
| `@HttpCode()` | 指定 HTTP 状态码；它和响应体里的 `code` 字段没有联动 |
| `@Response()` 陷阱 | 注入后必须自己 `res.send()`，否则请求超时，且 `return` 会被忽略 |
| Provider | 用 `@Injectable()` 标注、可被构造器注入的类；由「令牌 provide」+「实现 useXxx」组成 |
| 四种注册写法 | 语法糖 `[Service]`（最常用）、`useClass`（起别名）、`useValue`（注入现成值）、`useFactory`（工厂/异步） |
| 自定义令牌 | `provide: 'Xxx'` 必须配 `@Inject('Xxx')`，两边字符串要完全一致 |
| `useFactory` | `inject` 数组顺序必须与工厂函数形参顺序严格对应 |
| Module 四属性 | `controllers` 窗口、`providers` 员工、`imports` 借人、`exports` 授权 |
| 共享模块 | 提供方 `exports` + 使用方 `imports`，两件事缺一不可 |
| 全局模块 | `@Global()` 免除 imports，但仍需 `exports`，且必须被根模块导入一次 |
| 动态模块 | 静态方法 `forRoot(options)` 返回 `DynamicModule`，用于给模块传参；`providers` 与 `exports` 要引用同一个对象 |
