## 1. 实现了哪些功能

**全店设置。** 管理员可以统一填写固定运费、是否包邮、包邮门槛、完整退货地址、客服电话、可选服务时间和8项期限。页面用“元”输入金额，接口和数据库用整数“分”；拒绝超过两位小数、非整数期限、越界值和缺失资料。关闭包邮会保留门槛数值，是否参与真实结算由后续下单模块决定。服务时间留空会清除旧值。

| 期限 | 单位与可设置范围 |
|---|---|
| 付款等待 | 1～1440分钟 |
| 自动收货、售后申请窗口 | 各1～365自然日 |
| 售后审核、退货验收、退款处理 | 各1～30工作日 |
| 补充材料、寄回退货 | 各1～90自然日 |

这些是已实现的配置与计算规则；本板块没有自动关单、自动收货或真实退款功能。首次打开的金额和期限是表单建议值，地址、电话仍须管理员填写；保存前数据库保持未配置，有配置要求的业务明确拒绝继续。

**版本历史。** 每次有效修改必须填写原因，生成一个完整新版本，可以分页查看历史和旧版详情。相同配置重存不新增版本或审计；两个管理员拿同一旧版本修改，只允许一个成功，另一人收到409并须读取最新配置。新配置用于后续新阶段，已经开始的任务保留原设置版本、规则和截止时间。

**商城联系。** 顾客无需登录就能看到客服电话、服务时间，手机可点击拨号。公开接口只提供配置状态、电话、服务时间和版本号，不泄露退货地址或全店期限。未配置时显示维护空态；请求失败显示错误和重试，不把失败当成“没有配置”。

**任务工作台。** 员工可查看“我的待办”和符合自己当前全部权限的“岗位池”；管理员另有“待安排”。支持阶段、状态、业务类型、业务编号、当前逾期筛选及分页，进入详情再返回会保留筛选。详情显示经办、轮次、期限来源、原始截止、当前截止和历史；任务动作与期限事件合在一条分页时间线中，敏感原因按业务权限裁剪。

**领取和交接。** 同一个待领任务被多人同时领取，只能有一人成功。当前经办可在业务允许安全交接时填写原因释放；管理员可指派待领任务，或转交给启用、已改密且具备全部资格的员工。普通员工不能转交；交运未决等不安全状态不能借释放绕过处理。领取、释放、转交不增加任务轮次，也不重算期限。

**资格变化回池。** 停用员工、调岗或撤销个人附加权限后，失去资格的未完成任务同步解除经办、回到岗位池并提示管理员安排；仍合资格的任务不受影响。员工变化、会话撤销、业务经办、任务和审计同成同败，任一步失败整笔回滚。重新启用员工不会自动重新领取旧任务。

**期限与延期。** 统一按北京时间计算，数据库和接口保存UTC；分钟按经过时长，自然日按日历，工作日只计周一到周五，不接节假日和调休表。到截止的等号就算到期。管理员可在领域允许时延期，或给无默认期限的人工任务首次指定截止，均须填写原因；新截止必须晚于当前截止和现在。延期保留原截止和“曾逾期”，即使扫描尚未执行，也先补记旧逾期；首次指定不伪造原截止。

**轮次与共用任务。** 内核固定了20个阶段及资格来源，同业务同阶段只允许一个有效任务。相同动作重试返回原轮次；真实业务再次进入时先结束旧轮，再开新轮。还提供暂停、恢复、完成、取消以及多来源共用任务规则：一个来源结束不会提前结束其它来源，最后来源结束才按领域规则收尾。这些由后端领域服务调用，不开放任意创建任务或修改状态的HTTP接口；真实来源记录随后续业务仓储落地。

**超期扫描。** 正式环境启动时补扫，之后每分钟扫描。重复扫描、两实例同时扫描，同一任务同一截止只留一条逾期事实；超过一批的任务可继续扫描。一条失败不拖垮其它任务，记录脱敏原因和运行编号，下轮可重试；崩溃遗留的运行不会冒充成功。扫描只记录事实，不自动拒绝售后、关单或改变交运事实。

**暂停计时内核（BR-05）。** 自动收货从实际交运时间起算；交运未知不启动。第一个有效阻塞冻结剩余时间，后续阻塞不重复冻结；部分解除不恢复，最后一个解除才按“剩余时间与3自然日取较大值”恢复。再次暂停建立新周期，完成或退款终结计时；补录过去交运按真实时间计算。纯规则和事务端口已经验证，真实订单及阻塞表尚未开发。

**页面操作保护。** 提交期间禁用按钮、防止重复发送。版本冲突先重读；请求可能已成功但响应丢失时，锁住重试，先读取服务器结果，避免重复操作。退出登录清理内存查询，旧会话的迟到响应不能覆盖新登录。设置、任务和联系方式页面均覆盖电脑和手机。

## 2. 关键技术如何支持这些功能

| 做法 | 支持的具体功能 |
|---|---|
| 事务、行锁和版本号 | 先锁员工，再按固定顺序锁业务与任务，等待后重新核对身份和权限；避免同时领取、撤权后继续处理、旧页面覆盖新结果 |
| 数据库唯一约束与字段约束 | 保证同阶段有效任务唯一、轮次不重复、同截止逾期事件唯一；拒绝经办与状态不匹配的数据 |
| 完整快照和只追加历史 | 设置改版不重写旧任务；保留原截止、历次延期、曾逾期及操作原因，便于追溯 |
| 可注入服务器时钟与统一日历工具 | 页面、扫描、业务命令用同一时间规则；测试可验证周末、跨年和到期等号，无须修改电脑时间 |
| 业务适配接口 | Task内核负责通用规则，真实库存/订单/售后负责归属、权限、状态、锁和业务写入；尚未接入时明确拒绝，测试适配器不进入生产模块 |
| 运行锁、逐项事务和稳定分页 | 识别扫描崩溃、支持多实例重入与失败恢复，避免最早一批已扫描任务挡住后面的任务 |
| 复用认证、审计和生成客户端 | 沿用前三板块的登录/权限、requestId和错误外壳；前端直接消费后端生成契约，设置与任务共用无状态调用器，各自保留查询缓存 |

主要代码：`apps/api/src/settings/`负责配置，`src/common/time/`负责时间，`src/tasks/`负责任务、扫描和计时端口；员工回池接入`src/employees/`。后台页面位于`apps/admin-web/src/pages/`及`settings/`、`tasks/`，商城公开联系位于`apps/store-web/src/contact/`。设计细节见[实施设计](../../../docs/design/M0-04.md)。

## 3. 新增表、迁移和接口

迁移：`0004_store_settings_tasks_deadlines`，新增8张表，已应用到开发库。保留0001～0003，不原地修改已应用迁移；初始化只建立版本0的设置指针，不预填电话、地址、任务或订单。

| `task_history` | 领取、释放、交接、回池等动作及前后状态 |
| `deadline_event` | 逾期、延期、首次指定截止的独立事实 |
| `scheduler_run` | 扫描开始/结束、状态、数量和requestId |
| `scheduler_failure` | 扫描失败任务及脱敏诊断 |

本板块复用已有`audit_log`，没有新增Order、OrderBlock、TimerPause或生产任务来源表。

新增13个HTTP操作，以下统一带`/api/v1`前缀：

| 方法与路径 | 用途 |
|---|---|
| `GET /admin/settings`、`PUT /admin/settings` | 管理员读当前配置、完整保存新配置 |
| `GET /admin/settings/versions`、`GET /admin/settings/versions/{id}` | 分页历史、完整旧版详情 |
| `GET /store/contact` | 匿名公开联系资料 |
| `GET /admin/tasks`、`GET /admin/tasks/summary` | 三种任务列表与摘要 |
| `GET /admin/tasks/{id}`、`GET /admin/tasks/{id}/history` | 任务详情及统一时间线 |
| `POST /admin/tasks/{id}/claim`、`POST /admin/tasks/{id}/release` | 领取、本人安全释放 |
| `POST /admin/tasks/{id}/transfer` | 管理员指派或转交 |
| `POST /admin/tasks/{id}/extend-deadline` | 管理员延期或首次指定截止 |

设置、转交、延期分别使用已有管理员专属权限`store.setting.manage`、`task.transfer`、`deadline.extend`，不能通过个人额外授权下放。任务查询和领取还核对真实业务读取权、全部阶段资格及当前状态，管理员也不能跳过业务限制。全项目现为40个OpenAPI操作、38个生成JSON调用器；上传和二进制读取继续使用既有封装。
