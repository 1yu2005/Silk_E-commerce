## 1. 项目是怎么组成的

这是一个自营店铺系统：顾客站负责买东西，后台站负责店铺管理，两个网站都通过同一个后端处理业务，数据存进 PostgreSQL 数据库。

```text
self-ecom/
├─ apps/                    三个应用
│  ├─ api/                  后端：NestJS，接收请求、处理业务、连接数据库
│  │  ├─ src/               后端代码
│  │  │  ├─ common/         通用响应、错误处理、参数校验等公共能力
│  │  │  ├─ config/         读取并检查环境配置
│  │  │  ├─ health/         检查后端和数据库是否正常
│  │  │  └─ prisma/         后端连接数据库的代码
│  │  ├─ prisma/            数据结构定义、数据库迁移记录
│  │  └─ test/              后端测试
│  ├─ admin-web/src/        管理员使用的 React 网站代码
│  └─ store-web/src/        顾客使用的 React 网站代码
├─ packages/                三个应用可以复用的内容
│  ├─ shared/               公共接口类型
│  ├─ api-client/           前端请求后端的基础工具
│  └─ config/               公共代码检查、TypeScript 配置
├─ infra/                   Docker 构建、四服务启动、网站转发配置
├─ docs/                    技术实施方案、接口文档、测试证据
└─ 项目文档/                需求、板块设计、进度和学习总结
```

根目录的 `.env` 保存本机配置；`package.json` 定义常用命令；`pnpm-lock.yaml` 固定依赖版本。`node_modules`、`dist` 是安装或构建生成的内容，日常主要修改 `src`。

## 2. 板块1完成了什么 ⭐⭐⭐⭐⭐

**搭好工程**：后端、后台站、顾客站放在同一个工程里，用 pnpm 统一管理和启动。

**搭好两个网站外壳**：有首页、登录页面和找不到页面时的提示。登录尚未开放。

**接好数据库**：后端通过 Prisma 访问 PostgreSQL，建立迁移流程，并准备独立测试库。现在还没有商品、订单等业务表。

**统一后端基础规则**：返回数据和错误有统一格式；检查请求参数；记录请求日志，并给每次请求分配编号，方便查问题。

**加入健康检查和 Swagger**：能检查服务是否活着、数据库是否能访问；能在网页上查看和试调已有接口。

**做好 Docker 运行方式**：数据库、后端、后台站、顾客站四个服务可以一起运行，数据库和上传目录使用数据卷保存。

板块1已验收，94项普通测试和6项真实数据库集成测试通过。现在完成的是“地基”，登录权限、商品、库存和订单等功能要在后续板块实现。

首次运行或代码修改后，先构建镜像、启动数据库并应用迁移：

```powershell
docker compose --env-file .env -f infra/compose.yaml build
docker compose --env-file .env -f infra/compose.yaml up -d --wait db
docker compose --env-file .env -f infra/compose.yaml run --rm --no-deps api pnpm --filter @shop/api db:migrate:deploy
docker compose --env-file .env -f infra/compose.yaml up -d --wait --wait-timeout 90
```

以后没有修改代码和迁移时，日常启动只需上面最后一条 `up` 命令。每条命令成功后再执行下一条。

| 用途                | 当前本机地址                           |
| ----------------- | -------------------------------- |
| 后台站               | <http://localhost:8080>          |
| 顾客站               | <http://localhost:8081>          |
| Swagger 接口文档      | <http://localhost:8080/api/docs> |
| 直接访问容器后端的 Swagger | <http://localhost:3001/api/docs> |

容器后端的本机端口由 `.env` 的 `API_HOST_PORT` 决定，目前是3001；示例配置默认3000。两种启动方式使用同一个开发数据库。

查看服务状态、停止四个服务：

```powershell
docker compose --env-file .env -f infra/compose.yaml ps
docker compose --env-file .env -f infra/compose.yaml stop
```

**日常停止使用** **`stop`**，不要使用 `down -v`，后者会删除数据卷。

> 这两组运行方式的**主要区别是后端和两个网站在哪里运行，以及修改代码后如何更新。  🥸🥸🥸🥸🥸🥸🥸**
>
> | 对比项        | 第一组：本机开发               | 第二组：四服务 Docker      |
> | ---------- | ---------------------- | ------------------- |
> | 数据库        | Docker 中运行             | Docker 中运行          |
> | 后端和两个网站    | 本机运行                   | Docker 中运行          |
> | 修改代码后      | 通常自动更新，方便边写边看          | 需要重新构建镜像并更新容器       |
> | 运行条件       | 本机需要 Node、pnpm 和依赖     | 应用运行环境装在镜像里         |
> | 适合场景       | 日常写代码、调试               | 检查打包部署效果            |
> | 后台 / 顾客站端口 | 5173 / 5174            | 8080 / 8081         |
> | 后端端口（当前配置） | 3000                   | 3001                |
> | 如何停止       | `Ctrl+C` 停止开发服务，数据库仍运行 | Compose `stop` 停止容器 |
>
> 可以理解为：
>
> **后续开发用第一组；完成一个阶段后，再用第二组验证部署。** 当前两种方式共用同一个开发数据库，切换方式后数据仍然相通。

## API、配置与运行

正式业务接口只有`GET /api/v1/health/live`和`GET /api/v1/health/ready`。成功响应为`{data,requestId}`；错误为`{code,message,details?,requestId}`；X-Request-Id与响应体、日志一致。ready执行有界SELECT 1，故障503，live保持200。DTO管道仅校验声明DTO类的参数。

Swagger页面为`/api/docs`，原生JSON为`/api/docs-json`，开关关闭时均404；OpenAPI导出到`docs/openapi/openapi.json`。未提前添加Bearer鉴权或测试专用生产接口。

本机静态后台8080、顾客8081、容器API3001、数据库15432；开发服务为5173/5174/3000。容器内部API3000、数据库db:5432，浏览器调用同源`/api/v1`。完整配置与命令见[README](../../../README.md)。已有真实.env不覆盖、不提交。

迁移必须独立执行，不自动reset或在应用启动时迁移。容器统一入口：

```powershell
docker compose --env-file .env -f infra/compose.yaml run --rm --no-deps api pnpm --filter @shop/api db:migrate:deploy
docker compose --env-file .env -f infra/compose.yaml run --rm --no-deps api pnpm --filter @shop/api db:migrate:status
```

镜像包含Prisma及tsx，非root运行，关闭pnpm运行脚本前自动安装；修改依赖后重建。数据卷为self-ecom\_db\_data、self-ecom\_uploads；普通停止和重启保留卷，日常不使用down -v。上传卷可写且未暴露为静态目录，不代表文件上传业务已实现。
