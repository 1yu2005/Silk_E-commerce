## 1. 项目目标与边界

### 1.1 目标

为一家自营店铺建设以后台为重点的商品、库存、订单、发货、售后、顾客及经营管理系统。顾客端保持简单，支持从浏览、下单、模拟支付到收货与售后的完整闭环。业务正确性、操作可追溯性和跨岗位交接优先于页面装饰。

### 1.2 首期交付

- 后台管理站、顾客购物站、统一 NestJS API、PostgreSQL 16 数据库。
- 一家店铺、一个逻辑库存地点、普通实物商品、多规格 SKU、整单履约。
- 全额模拟支付和模拟退款；所有相关页面明确标记“模拟交易，不发生真实资金流转”。
- 电脑端页面，建议以 1366×768 及以上分辨率验收；不要求独立移动端适配。
- 本文要求的异常处理、待办、审计、定时任务及 Docker Compose 部署材料。

### 1.3 不在范围

多商家、多仓调拨、完整采购或盘点系统、真实支付、部分发货、拆包、部分退款、补发订单、电子面单、实时物流、在线聊天、短信验证码/通知、小程序/App、优惠券、秒杀、积分和会员等级。超期特殊售后、补发、转寄、额外运费赔付仅保留关联线下处理记录，不产生系统交易或自动库存动作。

### 1.4 规则来源与补充约定

标为 FR 的功能与通俗版各模块对应；BR、TD、NFR以及FR中的并发、数量边界和阶段限制是将其落实为可开发规则的补充。补充只消除歧义，不新增岗位、部分交易或聊天能力。通俗版的概括表述如“未退款关闭”“已发恢复计时”，须按本文细分阶段执行；已完成不重新收货、最终验收回补后不普通关闭。若需改变业务范围，应先变更通俗版，再同步本文及开发顺序，不能只修改页面文案。

本版补充基线：人民币单币种；金额用整数“分”；业务时区 Asia/Shanghai；截止时间包含等号（now ≥ deadline 即到期）；图片采用受控本地文件存储；员工用唯一账号名登录；分页默认20、最大100；同一商品最多3个规格维度、每维最多20个值、有效组合最多200个 SKU；后台商品轮播图最多10张。以上容量约定允许开发前调整，但必须前后端一致。

## 2. 技术与工程约束

| 编号 | 项目 | 要求 |
|---|---|---|
| TD-01 | 后端 | NestJS + TypeScript strict；Prisma；PostgreSQL 16；业务规则集中在应用服务/领域服务，Controller 不直接拼接跨模块事务 |
| TD-02 | 前端 | 后台与简单顾客端均为 React + Vite + Ant Design + React Router + Axios；TypeScript strict |
| TD-03 | 工程 | pnpm workspace + Turborepo；提交 lockfile，固定实际使用的兼容版本，不使用浮动 latest 作为部署基线 |
| TD-04 | 接口 | REST JSON，/api/v1 前缀；Swagger/OpenAPI；DTO 使用 class-validator/class-transformer；全局拒绝未声明字段 |
| TD-05 | 日志 | nestjs-pino；requestId 贯穿访问日志、异常和业务审计；日志脱敏，不记录密码、完整 JWT、Authorization、完整收货地址 |
| TD-06 | 身份 | bcrypt 存储密码；JWT 区分员工与顾客；服务端每次核验账号状态、会话有效性和最新权限 |
| TD-07 | 调度 | @nestjs/schedule；关单、自动收货、超期待办和交运核实扫描均可重入、可补跑 |
| TD-08 | 部署 | Docker Compose 编排 PostgreSQL、API、admin-web、store-web；两个前端以独立静态站点容器提供；单独迁移步骤；持久化数据库及上传目录 |
| TD-09 | 必要测试 | 单元测试 + PostgreSQL 集成测试 + 关键端到端流程；并发与数据库约束不能只用 Mock 验证 |

建议目录：apps/api、apps/admin-web、apps/store-web、packages/api-client、packages/shared、packages/config、infra。共享 API 类型/生成客户端，不向前端暴露 Prisma 模型、密码字段及服务端内部权限逻辑。

## 3. 术语与角色权限

### 3.1 术语

SPU：商品主体；SKU：实际售卖的规格组合；可售量 A：还能分配给新订单的数量；待付款占用 R：已下单未付款保留数量；已付款备货：已经从可售范围分配给订单的实物，不属于 R；交运：实际交给承运人，填写运单不代表交运；进行中售后：尚未拒绝、撤销、关闭或退款成功的售后。

### 3.2 权限矩阵（FR-01）

“全部”不意味着可以绕过状态、实物核实、经办人或记账规则。

| 权限组 | 超级管理员 | 商品与仓储 | 客服 |
|---|---|---|---|
| 员工账号、岗位、个人授权 | 全部 | 无 | 无 |
| 分类、商品、价格、成本、上下架 | 全部 | 全部 | 无 |
| 库存登记、入账、更正、预警 | 全部 | 全部 | 无 |
| 订单查询 | 全部 | 履约范围及必要收货信息 | 服务范围、付款退款、沟通记录 |
| 内部沟通备注 | 全部 | 仅有权业务记录，不可编辑客服备注 | 新增、更正说明，保留历史 |
| 发货领取、打包、交运、运单修正 | 全部 | 全部；完成/退款后的历史运单纠错除外 | 无 |
| 售后审核、材料要求、退款及重试 | 全部 | 无 | 全部 |
| 退货实物验收、可售量核实 | 全部 | 全部 | 无 |
| 顾客资料、完整地址簿查询 | 全部 | 无 | 有 |
| 顾客限制交易、冻结登录及恢复 | 全部 | 无 | 无 |
| 经营看板 | 有 | 有 | 无 |
| 全店设置、全店操作审计 | 全部 | 无 | 无 |
| 争议批准、特殊延期、跨人员转交 | 全部 | 提交意见 | 提交意见 |
| 手动关闭未付款订单 | 有 | 无 | 无 |

FR-02：实际权限＝固定岗位默认权限∪个人额外权限；不提供个人拒绝规则，不允许在个人页面取消默认权限。默认岗位权限由初始化权限表固化，首期不提供编辑岗位模板入口。

FR-03：额外权限只能从两个普通岗位业务权限集合选取；员工权限、设置、顾客账号状态、全店审计、争议特批等管理员专属能力不能下放。操作与查询依赖必须同时满足，如发货依赖履约订单查询；授权提交时自动补齐并展示依赖，撤销查询权限时同时撤销依赖它的额外操作权限。默认权限不能通过此方式间接移除。

FR-04：调岗清空额外权限并留痕。停用、撤权、调岗在下一次请求生效，同时扫描未完成待办，对不再有资格的任务解除领取、回到合资格岗位池，通知管理员重新安排。不能篡改已经成功的业务记录。

FR-05：初始化首个超级管理员，员工不自行注册。禁止停用或降级最后一个可用超级管理员；并发操作也必须保证此不变量。重置密码后撤销原会话，初始/重置密码登录后强制修改。

## 4. 功能需求

### 4.1 登录与账号（FR-10～FR-14）

- FR-10：员工账号名/密码登录；顾客手机号/密码注册登录；手机号唯一且格式校验，明确未进行实名或短信所有权验证。
- FR-11：顾客可修改昵称、头像、密码；密码修改验证旧密码，成功后撤销旧会话。密码建议8～64字符，bcrypt 输入不得超过72字节，前后端统一校验。
- FR-12：顾客状态分为正常、限制交易、冻结登录。限制交易只阻止新建订单，允许登录、期限内支付旧订单、收货及售后。冻结立即拒绝旧 token 和新登录，旧订单不取消。
- FR-13：员工/顾客登录限流，失败提示不泄露密码；注销撤销当前会话。JWT 载荷不得包含收货地址、手机号等不必要信息。
- FR-14：冻结顾客由客服在线下核实身份后代录原订单售后、材料、寄回物流及线下结果，记录来源、核实方式、经办人；仍受原售后期限、状态、验收和退款规则限制，超期走线下工单。

### 4.2 分类与商品（FR-20～FR-27）

- FR-20：分类最多三级，支持名称、图标、排序、父分类维护；同父级有效名称唯一（含根分类）。父级变更不得指向自身或后代，须锁定分类树稳定父记录，校验移动后整个子树深度≤3并同事务更新全部后代路径/层级；有子分类或关联未删除商品时禁止删除。前台父分类筛选包含全部后代分类。本期不强制商品必须关联叶子分类，不把通俗版未规定的叶子限制隐式加入。
- FR-21：商品维护名称、品牌文本、介绍、主图、轮播图、分类；首期品牌仅为字段，不新增独立品牌运营系统。描述使用纯文本或经过白名单净化的内容，不直接执行 HTML。
- FR-22：商品草稿、上架、下架；SKU 启用/停用。SKU 编号唯一，组合签名在同一 SPU 内唯一；单规格商品也须有一个默认 SKU。
- FR-23：支持颜色、尺码等规格组合生成、批量填价/成本/初始库存草稿。草稿允许未填价格/成本/图片，不完整时不得上架；一旦填写，售价须大于0、成本可空或不小于0，库存数量非负。启用销售SKU必须有有效价格；已有业务引用的SKU价格不得设空。初始库存不得随商品保存直接入账，应生成关联库存登记后确认。
- FR-24：上架要求必要资料、主图、有效分类、至少一个启用且价格有效/可售量大于0的 SKU；缺货后可保留展示但禁止购买。前台只展示上架商品及有效 SKU 的公开信息。
- FR-25：编辑商品不得覆盖库存；订单引用的商品/SKU不物理删除，使用停用/归档，保留库存账户、历史图片和快照。普通下架/停用/归档仅阻止新加购、新建单，不影响有效待付款订单按快照支付与已有订单履约售后；质量问题、实物不足等须另建关联订单异常，不能把普通下架当作取消订单。规格重建仅适用于无业务引用的组合，否则保留旧SKU并新增。
- FR-26：后台按名称、分类、状态、价格筛选，支持批量上下架并返回逐项结果；前台按名称/分类、价格/累计支付销量排序，使用稳定次序分页。SPU 展示价为启用 SKU 最低价。
- FR-27：图片上传校验真实格式、大小、数量；基线支持 JPEG/PNG/WebP、每张≤5MB，不接 SVG。商品公开图与售后私有凭证分开授权访问，历史引用的图片不得随意清理。

### 4.3 库存（FR-30～FR-37）

- FR-30：按 SKU 维护 A、R、预警阈值（默认10），A≤阈值提示；前台只显示可售量，不显示成本和占用明细。
- FR-31：人工库存登记类型含初始化、到货、可售损耗、更正；单据状态 PENDING/POSTED/VOID。待确认不生效，经办人确认后一次入账；允许同一人登记和确认，换人接手须领取。作废仅限待确认且须原因。
- FR-32：每单有唯一编号、来源、原因、附件、SKU明细、数量、创建/确认人及时间。所有人工修改含初始化、到货、损耗和更正统一走登记；商品页、库存页只是入口，不可直接改余额。已入账不可编辑/作废；更正单引用原单、实际差额和原因，校验非负、幂等及来源净入账。货已占用/售出导致可售不足时拒绝强制扣减，保持待核实，管理员协调相关订单后再更正。
- FR-33：来源凭据包含规范化来源标识、来源行、声明总数量、到货批次。相同来源行+批次只能入账一次；分批允许不同批次，累计净入账不得超过来源行核实数量，修改核实数量须原因和审计。内部损耗使用内部来源号及照片/说明；不能仅靠附件文件名识别来源。
- FR-34：自动占用、扣占用、取消释放、退货回补、未交运退款回补分别关联原业务和唯一动作键，禁止再建人工入库单重复加回。
- FR-35：可售损耗扣A；已付款备货损耗不再扣A，记录订单行损耗并限制退款回补。待付款占用实物不足时，锁定相关SKU及受影响订单，记录每行受损d（0≤d≤该行占用q），原子暂停SKU新购买并阻止受影响订单付款。支付与异常登记按同一锁序仲裁：支付先提交则按已付款备货异常处理；异常先提交则付款返回ORDER_STOCK_BLOCKED。无关旧订单不因SKU暂停一律禁付。核实未明时先保守阻止候选受影响单付款及自动释放，生成管理员超期待办；核实并分配d后，允许顾客/管理员关闭以及超时补扫，释放q与损耗d同事务，净A增加q−d，R减少q。阻塞不延长原付款期限，恢复后已到期只能关闭，不能付款；补齐实物后才能解除受影响付款阻塞。客服仅沟通，不越权手动关闭。
- FR-36：部分退货草稿/异常暂存不回补；整单验收完成或异常批准后的最终核实才按实际可售量一次性回补。每行 0≤可售数量≤实收数量≤应退数量；错货另记异常物品，不计原 SKU 实收，不虚填齐货。
- FR-37：流水可按SKU、类型、单号、时间、人员查；保存 A/R 前后值、差额、原因、业务引用和 requestId。库存不是完整实物总账，不能把 A+R 当成包括已付款备货和退货暂存的仓库总量。

### 4.4 购物车、地址与下单（FR-40～FR-47）

- FR-40：购物车须登录；同一顾客同一 SKU 唯一，重复加入合并数量，支持修改、勾选、删除。加入不留货，购物车中下架、停用、超库存项提示失效/不足。
- FR-41：地址新增、编辑、删除和默认地址，最多20条；并发新增不能突破上限；最多一个默认，删除默认后可无默认，由用户重选。收货人、电话、地区和详细地址必填。
- FR-42：结算预览返回商品现价、数量、商品总额、运费、合计、有效期和报价标识；服务器重新计算，不信任客户端金额。基线报价有效期5分钟，仅用于确认价格，不预留库存。
- FR-43：商品金额达到包邮门槛免运费，否则收固定运费；不使用成本、运费参与门槛判断；支持显式关闭包邮，门槛0表示全店包邮。
- FR-44：建单重新验证顾客交易状态、地址归属、商品状态、SKU价格、库存、运费。报价失效或价格/运费改变返回 PRICE_CHANGED/QUOTE_EXPIRED 和新预览，必须再次确认；库存不够返回 STOCK_INSUFFICIENT，不静默少买或提高价格。
- FR-45：Idempotency-Key按顾客+下单操作唯一。先验证身份/资源归属并查询幂等记录，再校验报价、当前交易状态及库存；已成功且同载荷则返回原订单，即使报价过期、商品下架或顾客后来被限制交易，也不再次建单。同键异载荷409；执行中返回409 REQUEST_IN_PROGRESS及重试提示。首次执行一次事务完成订单/快照、占用、购物车购买数量扣减、审计和成功幂等结果，失败全部回滚，不留永久执行中记录。同事务插入唯一键并处理并发冲突；同键并发只有一次执行。成功记录随订单保留且不复用；失败相同载荷可重试，新报价/地址/数量属于新载荷须新键。购物车并发新增数量不整行误删；取消订单不自动恢复购物车。
- FR-46：订单保存商品名/图/编号/规格/单价/成本、数量、收货信息、运费规则和金额快照；之后商品、地址、配置变化均不覆盖。金额满足商品总额＝Σ单价×数量，应付＝商品总额+运费。
- FR-47：未付款顾客可取消，管理员可填写原因关闭；其他员工默认不可手动关闭。已付款订单不能直接关闭，必须走售后。

### 4.5 模拟支付与订单（FR-50～FR-55）

- FR-50：支付页显示模拟标识、服务器金额、截止时间。首次支付锁定订单及相关库存，校验会话、归属、WAIT_PAYMENT、now<付款截止、受影响订单无库存付款阻塞；超期即使未扫描也不可付款。普通商品下架/停用不阻止已有有效单付款。成功WAIT_PAYMENT→WAIT_SHIPMENT、扣R不扣A，保存唯一成功支付、销量及发货任务；受损付款阻塞与关单规则按FR-35。
- FR-51：支付/取消/超时关闭并发只允许一次离开WAIT_PAYMENT，不把WAIT_SHIPMENT误称为订单最终终态。支付重试先查成功记录，有则返回该支付事实及订单当前状态（后来退款也不再次扣款）；无则按FR-50首次校验。不引入充值、余额或外部网关回调。
- FR-52：顾客按待付、待发、已发、已完成、关闭、退款筛选；“售后中”是组合筛选而非订单主状态。只能读取本人订单，后台查询也须按操作权限裁剪字段。
- FR-53：详情含金额及商品快照、收货快照、付款退款、运单、公开状态历史；后台额外展示授权范围内的内部备注/业务记录。内部信息不得通过详情、列表、导出或附件链接泄漏给顾客。
- FR-54：发货且无阻塞时顾客可确认收货；正常交运满10个自然日自动收货，以实际交运时间计算。主动/自动收货同时保存完成时间。
- FR-55：客服沟通记录为追加式，含渠道、时间、结果、下一步、公开说明/内部说明和附件；纠正以新增记录引用旧记录，不覆盖历史。普通员工不可改完成/退款后的历史运单，管理员纠错须原因并保留新旧值。

### 4.6 发货与异常（FR-60～FR-66）

- FR-60：一单一次整单发货、一个原始运单。领取→拣货打包→运单准备→开始交运→确认实际交运。履约进度独立于订单主状态。
- FR-61：领取须有权限且当前无经办人；同一环节只有一人，处理请求验证当前经办人。其他有权员工可以查看，不得重复处理。管理员接手也必须显式转交或领取。
- FR-62：开始交运在数据库中原子核验已付款、无进行中售后/暂停、当前经办人及全量商品，创建唯一交运动作并置交运中，然后才实际交包裹。填运单不能使订单变为已发货。
- FR-63：交运中申请售后可登记并暂停后续处理，但审核退款必须等待实物结果。交包成功登记失败不能回到普通待发货；客户端重试原动作，未确认动作保留，超时（建议5分钟）进入交运待核实。核实结果只能是已交运（登记实际交运时刻）、未交运（确认货仍在手）、继续待核实（仍禁止未发货退款）。不可仅凭超时自动认定未交运。
- FR-64：已领取未交运售后须仓储确认停止作业及货物位置；未开始处理的订单可由仓储领取核实待办确认。仅退款在未交运时也需要逐行确认可售/损耗，不能由客服猜测库存。回补规则见BR-04。
- FR-65：缺货、破损、错款等发货异常记录原因、照片，分别生成仓储核实与客服沟通任务。等待补货时，仓储确认齐货、客服记录顾客同意继续，两项均完成且无其他阻塞才能解除；退款时登记顾客同意并走整单售后。
- FR-66：运单修正须原因，保留原/新值；历史实际补发、转寄另记线下处理，不能覆盖成原发货。未付款改址取消重下；已付款未交运暂停、核实未交出、退款重下；已交运线下协调，首期禁止订单内改地址。

### 4.7 售后、验收与退款（FR-70～FR-81）

- FR-70：已付款且未全额退款订单可发起整单售后；未发货只能仅退款，已发货/完成可仅退款或退货退款；完成后7个自然日内可申请，已提交申请不因窗口届满失效。同时最多一个进行中售后；拒绝、撤销或关闭后可在原窗口内重新申请。超期特殊诉求仅记线下工单。
- FR-71：申请原因、说明、最多5张当前有效凭证，材料版本保留。顾客仅在当前PENDING_REVIEW且客服尚未给出同意/拒绝决定时可撤销，包含补充后回到待审核的情形；WAIT_SUPPLEMENT须联系客户服务人员登记关闭，不强制建立新申请。已同意、实物到仓或退款处理阶段不能自行撤销。
- FR-72：客服领取后同意、拒绝（必填原因）、要求补充（必填要求）；补充在原单提交，当前有效图总数≤5，可替换且历史可查；提交后回待审核、重新计算审核期限，历史逾期不删除。
- FR-73：售后进行中暂停发货和主动/自动收货。拒绝、撤销、允许阶段的未退款关闭仅解除本售后阻塞；其它异常保留。未交运且事实明确回待处理、原领取不自动恢复；交运中/不明保留核实任务，不能回UNCLAIMED掩盖已交运可能；已交运按事实保留SHIPPED。已发未完成只在最后阻塞解除时按BR-05恢复，已完成不退回已发货。最终验收/回补后关闭限制见BR-07。
- FR-74：退货同意时快照当时退货地址，展示顾客寄回入口；填写物流和实际寄出时间/凭据，单号不代表实际寄出。超时先跟进，有寄出凭据或运输中不能只凭超时关闭；核实未寄回后客服填写理由关闭，争议交管理员。
- FR-75：仓储实际收到包裹后登记 receivedAt，进入验收；逐订单行登记实收、可售、不可售、照片和原因。少件/错货/空包标验收异常，不完成整单验收，不回补部分可售量；客服要求补寄或核实，补寄批次累计核对，避免把同一物品重复计数。
- FR-76：整单齐货且检查完成可正常验收；因商品质量不可再售不能单凭此拒绝退款。验收后一次性回补可售量并交客服待退款，验收完成与退款成功是独立步骤。
- FR-77：验收争议由客服提交意见；管理员可批准异常全额退款，仓储最终确认真实实收/可售后回补一次，客服退款；或确认未退款关闭，必须记录物品保管/寄还安排、证据、原因及公开说明。管理员批准不允许虚填齐货或跳过最终实物核实。
- FR-78：仅退款无需退货验收。未交运须停止履约并生成绑定本售后、订单行和实物版本的核实记录，逐行确认可售/损耗，合计等于该行购买数量，未知数未清不得退款；未交运确认不等于可以售卖这些备货。发生损耗、货物移动或确认更正须先失效旧核实并递增版本，客服退款使用当前有效版本；关闭原售后后核实作废，新申请重新核实。已交运同意仅退款不回补，不允许用未交运核实替代退货验收。
- FR-79：退款金额固定等于唯一成功支付的全额（含原运费），不接受前端自填金额。审核通过不等于退款成功。每笔支付最多一个全额退款业务；失败沿用原业务重试，每次尝试独立记录。
- FR-80：模拟退款需支持开发/测试环境可控失败场景；失败不标订单已退款、不重复回补库存、不结束待办；同一业务并发重试只允许一次成功。成功后订单 REFUNDED、售后成功、任务关闭，不恢复履约或收货。
- FR-81：普通无理由退货顾客承担寄回费用；质量/错发由客服核实责任。额外费用/赔付仅线下协商记录，不计系统退款统计，不新增部分金额。

### 4.8 期限、待办、全店设置与审计（FR-90～FR-98）

| 阶段 | 默认期限 | 起算事件 | 到期处理 |
|---|---|---|---|
| 待付款 | 30分钟 | 下单成功 | 自动关闭并安全释放 |
| 自动收货 | 10自然日 | 实际交运 | 无阻塞才确认 |
| 常规售后申请 | 7自然日 | 确认收货 | 新申请拒绝，转线下诉求记录 |
| 售后审核 | 2工作日 | 首次/补充后待审核 | 超期待办，不自动拒绝 |
| 补充材料 | 7自然日 | 提出补充要求 | 跟进，不自动拒绝 |
| 寄回 | 7自然日 | 同意退货 | 人工核实，不自动拒绝 |
| 到货验收 | 2工作日 | 实际收包 | 跟进或登记异常 |
| 退款 | 1工作日 | 仅退款满足条件/验收完成 | 跟进或记录失败 |

FR-90：工作日按北京时间周一至周五，不接法定节假日/调休表。加 N 工作日跳过周六日并保留本地时分；周末起算先以起算时刻为基准逐日跳过非工作日，如周六10点+1工作日为周一10点。自然日为本地日历同一时刻。日期以服务端为准。

FR-91：每阶段存起算、截止、规则快照、延期历史和逾期事件；改全局期限仅影响之后进入的新阶段，不回写已生成截止时间。管理员可填写原因延期，历史逾期仍可查询。售后申请窗口在完成时固化，付款期限在下单时固化。

FR-92：任务含业务单、环节stage、轮次round、候选权限、经办人、状态、dueAt、历史。领取/转交/回池原子留痕；同一业务同一环节最多一个有效任务，历史完成任务不阻止阶段重入。材料补充后重新审核、补寄后再次验收、售后关闭后重新领取发货均递增轮次，生成新任务和期限；同一轮幂等重试不得再增轮次。阶段完成与新任务生成同事务，旧经办人不自动继承，合资格人员重新领取（同一人可再领取）；退回岗位池只是解除当前轮领取，不另起轮次。

FR-93：只允许有当前实际权限且已领取任务的人员处理；管理员接手也显式转交。允许仓储核实与客服沟通分别有任务；同一业务同一环节同一轮唯一，且该环节最多一个有效任务。到期扫描只标记及记事件、不重复造任务。账号变更时即时重新校验处理资格并回池；前台刷新/进入工作台展示提醒，不要求推送、短信或聊天。

FR-94：全店设置含固定运费、包邮开关/门槛、退货地址、客户服务联系方式、各阶段期限。权限仅管理员；修改有版本及审计；退货地址同意时快照，运费下单时快照。

FR-95：顾客资料包含注册/最近登录时间、地址、订单、累计净消费。商品与仓储只能查看履约所需数据。累计净消费＝当前已完成且未全额退款订单的实付总额；完成后退款需扣回，不将未收货支付额计为已完成消费。

FR-96：经营看板按北京时间统计：今日订单数（创建时）、新顾客（注册时）、支付额（成功时）、退款额（成功时）、净收款＝支付额−退款额；允许负值。提供7/30天趋势、30天热销（区间成功支付件数，退款不追溯扣减，注明口径）、待发货、售后暂停、待审、失败退款、库存预警。支付销量排序为历史成功支付件数，不因退款倒扣；不同于累计净消费。

FR-97：关键业务追加不可随意修改的审计：操作者/系统任务、时间、对象、动作、原因、必要的变更前后值、requestId。失败请求进技术日志，成功关键变更与审计同事务。业务账户无修改/删除历史流水与审计的接口；数据库运维权限另行管理。

FR-98：后台按操作者、类型、业务号、时间分页查审计；脱敏展示，联系方式按使用场景裁剪。顾客侧只展示审核结果、要求、公开说明、物流及凭证，不展示员工个人资料/内部讨论。

## 5. 核心状态与不变量

### 5.1 订单主状态（BR-01）

| 当前 | 动作/条件 | 目标 |
|---|---|---|
| WAIT_PAYMENT | 期限内、无受影响库存付款阻塞且模拟付款成功 | WAIT_SHIPMENT |
| WAIT_PAYMENT | 顾客取消/管理员关闭/超时 | CLOSED |
| WAIT_SHIPMENT | 实际交运确认成功 | SHIPPED |
| SHIPPED | 无阻塞的主动/自动收货 | COMPLETED |
| WAIT_SHIPMENT/SHIPPED/COMPLETED | 全额退款成功 | REFUNDED |

CLOSED、REFUNDED 不继续支付/发货。售后失败不把 COMPLETED 改回 SHIPPED。已交运的事实即使售后中也须补录，不能因暂停拒绝登记真实事实。

### 5.2 履约、阻塞与售后状态（BR-02）

履约阶段：UNCLAIMED→PREPARING→READY→HANDOVER_IN_PROGRESS→SHIPPED。交运未知进入HANDOVER_UNCERTAIN；确认未交运且无售后/阻塞可回READY，有售后则保持停止作业；确认已交运补录SHIPPED及真实时间。未交运售后未退款结束，只有交接事实明确才回UNCLAIMED并新轮领取；未知状态保留原交运动作及核实任务。一个订单可有多次失败/确认未交的交运尝试，但最多一个未决动作、一次真实整单交运；原动作重试不新建尝试。

阻塞使用独立记录：AFTER_SALE、SHIPMENT_EXCEPTION、HANDOVER_UNCERTAIN、ADDRESS_REQUEST、STOCK_EXCEPTION，可同时存在。解除一个不能清空其他阻塞。放行函数统一校验主状态、履约状态、阻塞、售后和经办人。

售后：PENDING_REVIEW→WAIT_SUPPLEMENT→PENDING_REVIEW；待审可REJECTED/WITHDRAWN（按FR-71）。同意仅退款：未交运或交接未知进入WAIT_FULFILLMENT_CHECK，核实当前有效版本后WAIT_REFUND；确认已交运且同意无需退货可直接WAIT_REFUND。若核实期间确认已交运，记录申请人接受“无需退货全额退款”的客服决定再进入WAIT_REFUND，不能静默换成退货退款。退货路线：WAIT_RETURN→WAIT_RECEIPT→WAIT_INSPECTION→WAIT_REFUND；不齐货进入INSPECTION_EXCEPTION，可补寄重入待收/验收，或管理员决定后FINAL_INSPECTION→WAIT_REFUND。退款WAIT_REFUND→REFUNDING→SUCCEEDED/REFUND_FAILED，失败重试REFUNDING；实物核实失效则未交运仅退款回WAIT_FULFILLMENT_CHECK，仍复用同一退款业务。CLOSED只能按BR-07从允许阶段进入。REJECTED/WITHDRAWN/CLOSED/SUCCEEDED为终态，其余为进行中。

退货已实际到仓时允许有权仓储登记到货而不强依赖顾客已填单号，但须补录来源/原因并留痕。异常批准后最终核实的动作不与普通验收混用。状态迁移使用命令接口，禁止任意 PATCH status。

### 5.3 库存记账（BR-03）

| 事件 | A变化 | R变化 | 说明 |
|---|---|---|---|
| 人工确认到货/初始化 | +q | 0 | 唯一来源/批次 |
| 创建待付款订单 | −q | +q | 校验A≥q |
| 模拟付款成功 | 0 | −q | 成为订单备货，不再次减A |
| 未付款正常关闭 | +q | −q | 仅一次；受损d已核实则净增加q−d，未核实进入超期核实待办，不盲目释放 |
| 可售实物损耗 | −q | 0 | A不能为负 |
| 已付款备货损耗 | 0 | 0 | 记录订单行损耗，不能二次扣A |
| 未交运仅退款回补 | +s | 0 | s为核实可售量 |
| 已交运仅退款 | 0 | 0 | 不要求退货，不回补 |
| 整单验收完成/批准后的最终核实 | +s | 0 | 草稿和部分实收不回补 |

A/R永不为负；不得直接修改R。更正必须差额流水。异常待付库存取消时，将待释放q中受损d以关联损耗在同一事务落账，净A增加q−d，R减少q，不能先提交释放再单独扣损耗。

### 5.4 回补、退款、计时及结案（BR-04～BR-07）

BR-04：未交运仅退款在退款成功事务校验核实版本仍有效、未交运事实、无未决交运动作及逐行数量，回补s并记录损耗；失败不回补。该货物在此之前仍为原订单备货，不可重复入账或转卖。退货退款在最终验收事务回补，与退款成功分离；最终结果不可直接改写，重试只重做退款不重验收。核实若与并发损耗冲突，退款返回PHYSICAL_CHECK_STALE，由仓储重新核实；退款先成功后发生的实物损耗改走可售库存损耗。全额退款不等于全量回补。

BR-05：仅SHIPPED且未完成的订单有自动收货计时。首个阻塞生效时保存remaining=max(原截止−暂停时刻,0)，同一暂停周期其余阻塞只关联原因，不重复冻结。部分解除时不生成生效截止；最后一个阻塞解除时，新截止=实际解除时刻+max(remaining,3自然日的时长)，并结束本暂停周期。下一次真正暂停新建周期，重试不重复延长；COMPLETED保持完成，REFUNDED不恢复。交运事实补录以实际时间建立基础截止；若此时仍有售后阻塞，冻结当前剩余时长，全部解除再恢复。任何未知交运不能启动收货计时。

BR-06：退款全业务唯一、每次尝试有独立编号与结果；模拟执行与结果可直接在单事务持久化，失败尝试单独落记录，业务仍可重试。本期不设计外部支付回调/分布式支付一致性，但必须防并发和进程重启重复提交。

BR-07：关闭售后不是任意阶段的通用出口。WAIT_SUPPLEMENT、未实际寄回的WAIT_RETURN/WAIT_RECEIPT，客服核实说明原因后可关闭；待审直接拒绝或按FR-71撤销。已寄出/部分到仓/验收异常的结案须管理员决定并记录物品去向，且此前尚未最终验收、尚未回补、没有退款处理中或成功。未交运核实后关闭也必须没有实际退款尝试，由管理员确认停止退款并失效核实。进入REFUNDING/REFUND_FAILED，或任一路线最终验收回补后，不允许普通或管理员直接CLOSED，只能完成必要核实并继续退款/失败重试；本期不做最终验收撤销与库存冲正流程。REJECTED/WITHDRAWN/CLOSED不回退历史资金与实物事实。

TD-11：资金、库存、状态、任务及审计同事务；关键命令在事务内再次校验最新身份/权限/经办人，不仅依赖Guard。账号和授权变更与关键业务锁同一主体记录，按取得锁的先后仲裁，变更提交后的新请求不得用旧权限。统一锁顺序：员工主体（涉及时）→顾客主体（涉及时）→共享分类树锁（涉及时）→已有订单按ID升序→商品按ID升序→SKU/库存按ID升序→来源行按ID升序→售后/任务及其它附属记录；不需要的锁跳过但不逆序。新建订单尚无既有订单锁，商品/库存后插入新订单；库存异常需先确定候选订单后按上述顺序取锁，再验证关联和数量，若候选变化回滚重试。任务、验收、退款、支付、下架、核实更正均遵守顺序。死锁/Serializable冲突有限重试整个命令（最多3次）并沿用幂等键，库存不足不重试。

TD-12：禁止读库存后无条件写回；采用带库存条件的原子扣减并检查影响行数。库存更新、流水、订单行快照任何一步失败整单回滚。最后管理员保护、地址上限、来源累计入账等跨行不变量也须锁定稳定的父记录后验证。

## 7. 接口与页面基线

### 7.1 接口规范

TD-13：成功返回 {data,requestId}，分页为 data:{items,total,page,pageSize}；错误为 {code,message,details?,requestId}。HTTP语义：400校验、401未登录/失效、403无权限、404不存在或不属于当前顾客、409状态/并发/报价冲突、429限流、500系统异常。错误不返回堆栈/SQL。所有对象级权限在服务端检查。

TD-14：时间ISO 8601 UTC传输、timestamptz存储，北京时间展示。金额以整数分使用PostgreSQL INTEGER和JS安全整数，不用浮点元：售价及非空成本单价≤1,000,000分、包邮门槛≤100,000,000分、单行数量1～99、订单≤100行、运费≤1,000,000分、订单应付≤100,000,000分；任何乘加、设置和汇总使用安全整数校验，单笔字段CHECK限界，聚合SQL使用BIGINT并在API以十进制整数字符串传输（不直接JSON序列化BigInt），前端格式化元不参与浮点计算。报价、下单、支付、退款统一边界；数量为整数、布尔严格转换、排序白名单。Swagger明确单笔金额number、统计金额字符串、鉴权、幂等及错误。

## 8. 非功能与交付要求

- NFR-01 安全：bcrypt cost建议12并实测；JWT建议2小时且可撤销；首期不强制实现refresh token。每请求查会话与账号/最新权限，不能只相信token中的旧权限。员工和顾客登录域隔离，密码字段默认不参与序列化。
- NFR-02 前端token基线存内存+sessionStorage、关闭标签页不保证退出所有会话；严禁localStorage存明文密码。登录/上传限流，CORS限定两个站点来源；非演示公网部署需HTTPS、替换初始密码及生产密钥。
- NFR-03 上传目录持久化，不写入容器临时层；随机命名、防路径穿越；售后私有凭证不得作为公开静态目录暴露。单次业务提交校验资源归属及有效图片数量。
- NFR-04 查询有分页、必要索引，列表禁止逐行查询；列表建议p95≤500ms、常规写入≤1s（不含上传），验收环境记录机器配置；基线10万订单/100并发查询，仅为验证目标，不能未经压测声称达标。
- NFR-05 至少验证100个并发请求抢同一SKU有限库存不超卖、20人抢同任务仅1人成功；模拟重复退款/入账各100次不重复记账。
- NFR-06 API提供存活/就绪检查，数据库不可用就绪失败；调度可批处理、索引扫描、失败记录和恢复补扫。即使两个实例同时扫描也不可重复转态；单机Compose不代表无需并发防护。
- NFR-07 设置、历史单据、来源凭据、库存流水和审计不提供随意删除接口；数据库每日备份示例及恢复步骤随README交付，演示一次恢复。日志滚动，不把日志当业务账本。
- NFR-08 Compose含健康检查、数据库持久卷、上传卷、环境变量样例；前端构建变量仅为公开配置，JWT/数据库密码不打包入前端。API用服务名连接db；静态站点支持React Router history回退与/api反向代理。
- NFR-09 提交Prisma migrations、幂等seed、权限清单、OpenAPI、演示数据、启动/迁移/备份说明、自动化测试及验收记录。种子不能覆盖已有生产账号密码或重置库存。
- NFR-10 完整工程检查：pnpm安装可复现；turbo lint/typecheck/test/build；数据库集成测试使用PostgreSQL16；前后端与Docker构建通过。只对Markdown检查不能替代系统验收。

| AC-28 | 售后结案后另一个阻塞延迟5天解除，最后解除时才生成截止且至少再留3天；重叠阻塞不重复冻结，完成/退款订单不恢复计时 |
| AC-29 | 员工创建、授权、重置及停用审计失败则业务回滚；撤权与敏感命令并发按主体锁顺序仲裁，变更后请求不能越权 |
| AC-30 | 商品普通下架/停用仍能支付旧有效单；新下单拒绝；与建单并发按商品锁提交顺序取合法快照；金额超限拒绝；分类移动校验整个子树并更新路径 |

AC-19中的成本权限：商品与仓储/超级管理员可读；客服订单查询不默认展示成本。验收使用含多SKU、缺货、退货及历史退款的种子数据，不仅演示单商品成功支付。

## 10. 需求变更与完成定义

每个模块完成须同时满足：接口契约与权限明确、状态命令实现、数据约束/迁移提交、对应页面可用、关键异常/并发测试通过、Swagger与操作说明更新。本文为计划和验收基线，不是已实现证明。

后续变更需记录需求编号、原因、影响实体/状态/权限/API/页面/用例、是否迁移旧数据；修改本文与配套顺序文档版本。不得为赶进度删去库存不变量、实际交运核实、退款幂等和审计，也不得未经范围变更加入真实支付或部分退款。
