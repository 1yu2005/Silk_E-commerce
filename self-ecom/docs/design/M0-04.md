## 步骤1：服务器时钟与期限计算

| 文件 | 职责 |
|---|---|
| `apps/api/src/common/time/clock.ts` | 抽象Clock注入令牌及真实SystemClock，每次读取返回独立Date |
| `apps/api/src/common/time/time.module.ts` | 显式导出Clock，后续业务模块按需导入；本步不注册到AppModule、不注册路由或定时器 |
| `apps/api/src/common/time/deadline.ts` | 纯期限计算、到期判断及可用于快照的时区/算法版本常量 |
| `apps/api/test/time.spec.ts` | 日历、到期边界、输入失败、时钟替换与不同宿主时区的定向测试 |

内部调用约定：`calculateDeadline(startedAt, { unit, amount })`返回新的Date，序列化使用`toISOString()`输出UTC。unit仅为MINUTE、NATURAL_DAY、WORKDAY，amount须为正安全整数；配置字段自身的业务上限留给设置DTO和数据库CHECK，不由时间工具冒充配置校验。

`isDeadlineReached(now, dueAt)`按`now >= dueAt`判断，等号即到期；无效Date明确失败，不误返回“尚未到期”。调用方从Clock取服务器时刻，后续敏感命令在持锁后重新取时核验，不依赖客户端倒计时或扫描是否执行。

### 日历语义

- 分钟按真实经过的毫秒相加。
- 自然日按`Asia/Shanghai`本地日历加日，保留时分秒和毫秒。
- 工作日从起算日之后逐日计数，只计周一至周五；周六/周日加1工作日均为下周一同一时刻。先推进整周再处理余数，避免巨大数量引发长循环。
- 使用原生Intl读取指定IANA时区字段，用UTC日历方法做日历运算，再按指定时区还原真实时刻；不调用依赖宿主时区的日历方法，不新增日期库。
- 算法版本为`shanghai-calendar-v1`。覆盖上海历史夏令时，重复本地时刻固定取较早时刻；历史跳时导致目标本地时刻不存在时明确失败，不能偷偷改变时分。当前项目期限使用现代北京时间，该历史边界策略不改变现有业务。
- 不支持0期限、不接节假日/调休表。无SLA由调用方保留null，不调用工具补默认截止。不会修改原Date或输入规则。

## 步骤2：设置、任务与期限的数据基础

正式迁移为`apps/api/prisma/migrations/0004_store_settings_tasks_deadlines/migration.sql`，Prisma模型在`apps/api/prisma/schema.prisma`，不修改0001～0003。迁移整体使用事务，新建8张表；只插入Head的`id=1,current_version_id=null,version=0`，地址/电话无默认值，不生成设置版本、任务或业务单。

| 表 | 如何支持后续功能 |
|---|---|
| store_setting_head | 单店稳定锁行；当前版本指针与编号通过复合外键保持一致 |
| store_setting_version | 完整设置历史快照，金额、8项期限、地址电话和修改原因有字段底线 |
| task_stage_cursor | 同业务同阶段的稳定轮次锁锚点，lastRound不得为负 |
| task | 保存轮次、资格、经办、期限和规则快照；同阶段有效任务部分唯一 |
| task_history | 保存任务动作、主体、经办前后状态、动作键与requestId |
| deadline_event | 分开保存逾期、延期、首次指定；同任务同截止的OVERDUE部分唯一 |
| scheduler_run | 保存调度生命周期、数量和独立requestId |
| scheduler_failure | 保存所属运行、可选任务和限制长度的脱敏错误摘要 |

关键数据库约束：

- Head固定单行，空指针仅对应版本0，非空指针及版本号必须匹配同一Version。
- Task与Cursor使用`cursorId,businessType,businessId,stage`复合外键，数据库拒绝借用其它业务游标；阶段与业务类型是固定枚举组合。
- 同业务同阶段的round和entryKey分别唯一；OPEN/CLAIMED/SUSPENDED共同占据一个有效位置。Task经办只有CLAIMED可非空，终结任务须有结束时间，截止不得早于起算或原截止。
- 历史记录的员工主体、经办前后状态及真实员工外键受约束。旧状态为null时用CASE明确要求原经办为空，避免SQL三值逻辑绕过CHECK。
- 资格JSON须为非空字符串代码数组，规则快照须为JSON对象；固定阶段具体权限、真实业务归属、完整快照字段由后续服务校验，数据库不会把任意UUID当作真实订单。
- 逾期发生时刻等于截止事实，检测时刻不得早于发生；延期/首次指定须有新截止和原因。历史逾期与当前期限分别保留字段。
- 关系采用RESTRICT保护已有历史；调度计数非负，运行状态与结束时间一致。错误列限制长度，但脱敏内容仍须后续扫描服务主动生成。

`TaskActorType`只允许EMPLOYEE/SYSTEM。顾客的真实动作保存在对应业务历史；由顾客动作派生的内部任务历史使用系统主体，后续服务需写明来源，不把顾客当员工经办。

本步没有添加禁止UPDATE/DELETE的数据库触发器。设置版本/历史只追加、原截止不可变、everOverdue不可清除、轮次递增及合法状态流转，均须后续正式命令服务与事务测试保证；不能以字段CHECK代替这些验收。

## 步骤3：全店设置后端

### 文件与接口

新增`apps/api/src/settings/`，包含DTO、服务、控制器、OpenAPI、错误与模块；AppModule注册StoreSettingsModule。模块显式导入既有认证/审计及步骤1的TimeModule，不新增依赖、迁移或环境变量。

以下路径统一以`/api/v1`为前缀：

| 方法/路径 | 权限与结果 |
|---|---|
| GET /admin/settings | store.setting.manage，返回configured、version、currentSetting；未配置时false/0/null |
| PUT /admin/settings | 同权限，完整设置+expectedVersion+reason；返回version、settingVersionId、changed、currentSetting |
| GET /admin/settings/versions | 同权限，严格page/pageSize，编号倒序摘要分页 |
| GET /admin/settings/versions/:id | 同权限，UUID版本详情及原因；不存在404 SETTING_VERSION_NOT_FOUND |
| GET /store/contact | 无需登录，仅configured、servicePhone、serviceHours、settingsVersion |

currentSetting和版本详情含id、versionNumber、createdByEmployeeId、createdAt、reason及运费/地址/联系/期限。摘要仅ID、编号、修改人ID、时间及原因。所有接口no-store，继续使用统一data/requestId和脱敏错误外壳。

### 完整输入、版本与事务

- PUT必须提供全部经营配置和8项期限，不在服务里补默认金额、地址或电话。严格数字、整数、boolean；嵌套对象使用Type+ValidateNested+IsDefined+IsObject，拒绝数组、null、缺字段及嵌套未知字段。
- 文本去首尾空白。电话输入只允许可选`+`、数字、空格和连字符；去首尾空白后的输入及规范化结果都限制3～30，保存时移除空格/连字符。serviceHours省略、null或空白均保存null，并清除上版值；其余字段仍必填。
- 写入复用runAuthTransaction：员工行锁→Head行锁→重新认证会话/当前岗位/强制改密状态及store.setting.manage→比对expectedVersion。设置不变更管理员集合，不另取集合锁，也不在持Head时反向锁员工。
- 先验证版本，再比较规范化后的配置。同内容只返回现版changed=false；单独改reason也不造新版本，过期版本提交相同内容仍409。
- 有效变化只INSERT新Version，再更新Head并追加AuditLog；Clock提供createdAt，写入失败整体回滚。旧Version不UPDATE；已有Task的设置来源、originalDueAt、dueAt和ruleSnapshot不回写。
- 查询当前配置/公开联系、历史分页采用RepeatableRead快照，避免版本指针、总数和结果来自不同时点。
- 导出的`StoreSettingsService.requireCurrent(tx)`供后续领域在自身事务读取原始版本；未配置抛409 STORE_NOT_CONFIGURED，不创建业务假数据或自行补默认配置。

## 步骤5：固定阶段、真实业务接入与阶段进入

### 固定目录与接入边界

新增`apps/api/src/tasks/`，AppModule注册TasksModule，导出TaskBusinessAdapters和TaskEntryService。目录精确覆盖现有20个TaskStage，版本为`M0-04.stages.v1`；资格取固定权限码并展开既有依赖、去重排序和深层冻结，只用于判断，不给员工自动增权。

只有审核、补材料跟进、寄回跟进、验收、退款五类阶段引用设置中的期限；其余阶段无默认SLA，dueAt、originalDueAt、settingsVersionId为null。有SLA但尚未配置时明确409 STORE_NOT_CONFIGURED，不自行采用文档建议值。新任务保存实际阶段起算时刻、当前设置版本、规则来源/字段/数值/单位、北京时间、算法版本及目录版本；不回算旧任务。

真实领域通过启动注册适配器和相应锁处理器接入：

- `planLocks(tx,reference)`只读定位完整上游对象，不取锁、不写库或调用外部服务，至少包含本业务稳定根记录。
- `authorize(tx,reference,actor)`在完整锁取得后核对真实实体、归属、当前主体。幂等重放也执行授权；顾客检查本人归属，不要求员工资格；系统动作由领域确认允许条件。
- `resolveEntry(tx,entry,actor,activeTask)`验证真实状态与语义动作键，给出可信起算时刻；新轮替换必须明确提供旧任务ID、expectedVersion和COMPLETED/CANCELLED结果。业务须禁止把退款失败重试等同轮动作当作新阶段进入。

生产注册表保持空：ORDER、AFTER_SALE、INVENTORY_ADJUSTMENT、OFFLINE_CASE、CUSTODY_ARRANGEMENT均默认409 BUSINESS_MODULE_NOT_READY。没有假订单、假售后、开发任务或任意创建/完成/取消任务HTTP；没有新增迁移、依赖、必要环境变量或客户端契约。

### 调用方事务与完整锁计划

调用方先开启自身事务，在任何领域行锁之前进入`withContext(tx,access,references,requestId,command)`。端口拒绝根PrismaClient，预定位所有相关CLAIMED经办，连同当前员工一次按ID升序锁完；顾客、分类树、订单、商品、SKU/余额、库存来源及各领域根记录按固定层级合并、去重、每层ID升序锁定。SKU及余额由真实库存模块在同一资源处理器中遵循既有顺序，不新造通用库存表。

取得全部上游锁后重读锁计划与经办；集合变化就抛TASK_LOCK_PLAN_CHANGED，要求外层回滚整个命令、重新定位，不能在持任务/库存锁后补员工或订单锁。本端口不自动开启事务、不自动重试；后续领域命令应按TD-11以相同语义键有限重试整个命令，不能把这里描述成已有自动重试能力。

随后复核真实会话、当前岗位/权限、停用和强制改密状态，并逐个执行领域授权。WeakMap签发上下文，只在该回调期间有效；伪造、跨业务或回调结束后重用均拒绝。回调可以先改变真实领域状态再进入阶段；任何异常必须传播至最外层事务。新建任务等待游标/任务或领域检查后，写入前再次认证、授权，覆盖等待期间凭证到期。

### 幂等、新轮与同事务事实

`enterStage(context,input)`只接受业务引用、固定stage、entryKey和reason，不传播调用方夹带的资格、经办或期限。相同业务/阶段/entryKey返回原任务changed=false，包括已结束的原轮；不重算、不复活、不追加历史审计。新键使用稳定Cursor行仲裁，按Cursor→Task顺序锁定，以lastRound+1建立新轮，禁止SELECT max+1。

存在OPEN/CLAIMED/SUSPENDED旧轮时，只有领域明确确认且版本匹配才允许结束并替换。旧任务结束、清经办、版本递增，新任务OPEN/经办为空、重新固化规则和截止，与Cursor、CREATED/终结历史、最小审计及领域变更一起提交；无明确替换返回TASK_STAGE_ACTIVE，版本冲突返回VERSION_CONFLICT。

替换时旧截止已到（含等号），先按真实dueAt补记OVERDUE事件；occurredAt为截止，detectedAt为当前时刻，唯一事实去重，保留更早firstOverdueAt和everOverdue。新轮不继承旧逾期。该处理只服务本步领域重入，不代表统一扫描器已实现。

沿用已冻结TaskActorType：员工历史记真实员工；顾客驱动历史记SYSTEM，真实顾客主体保留在AuditLog，后续真实领域历史仍须保留顾客原动作。审计仅增加task.create、task.stage.complete、task.stage.cancel、task.overdue.record四个受限动作，使用独立taskStatus字段，不放宽原员工status白名单或旧动作主体。

### 当前边界与下一步

本步通过独占库真实行锁/领域夹具验证阶段进入，测试表和适配器只在`apps/api/test/`，不进入生产模块；实际订单/售后时间点、动作键及完整流程仍由后续板块接入补验。领取、释放、转交、资格回池、资格变化、通用领域结束端口、延期、扫描和BR-05尚未实现。

下一步拟接任务查询、领取与本人释放，在任务服务、HTTP/生成契约中处理资格、版本冲突、经办及历史审计；按小步骤继续，收到用户下一次“执行”后实施。管理员转交/同步回池及后续能力另行推进，整板块交付文档仍待统一收尾。

## 步骤6：任务查询、领取与本人释放

### HTTP与公开范围

TasksModule新增六个员工接口，统一`/api/v1`前缀、Bearer、no-store和data/requestId响应；没有新增通用创建、完成、取消或PATCH状态接口。

| 方法/路径 | 当前行为 |
|---|---|
| GET /admin/tasks | view默认mine，当前本人经办；pool为当前合资格OPEN；reassign仅SUPER_ADMIN且task.transfer，返回有效且reassignNeeded的任务 |
| GET /admin/tasks/summary | 本人未完成、合资格待领、当前逾期、历史曾逾期；管理员额外待安排数，普通员工该值null |
| GET /admin/tasks/:id | 任务与轮次/期限快照、当前经办显示名、动作提示、真实领域裁剪的业务摘要和最近期限事件 |
| GET /admin/tasks/:id/history | TaskHistory与DeadlineEvent统一时间线，发生时间降序、kind/id升序稳定分页 |
| POST /admin/tasks/:id/claim | expectedVersion，完整资格且真实业务允许时领取本人 |
| POST /admin/tasks/:id/release | expectedVersion和reason，仅当前经办且确认安全交接时释放 |

查询支持stage/status/businessType/businessId/overdue及既有严格分页；overdue只接受true/false，版本必须原生非负整数，拒绝字符串、数组、未知字段或客户端经办/状态/资格。释放原因去首尾空白并按Unicode码点限制1～500。列表按截止升序（无截止最后）、创建时间和ID排序；超大页通过既有paginationWindow安全返回空，不能把不安全偏移传数据库。

### 真实读取与交接适配器

在已有业务注册表上增加独立`registerAccess(type,access)`，须先注册真实业务；重复或不完整注册拒绝。读取/交接接口与阶段进入接口分开，避免用“能创建下一阶段”的权限代替读取历史或安全交接条件。

- `visibleBusinessIds(tx,actor)`返回当前主体确实有业务读取权、且真实存在的业务ID。首期小店采用这个授权集合查询，不接受浏览器提供授权范围；业务量扩大后可结合真实领域表优化集合查询，不先搭建通用工作流。
- `describe(tx,actor,task)`只读给出业务号、标题、安全应用内详情路径（未接页面时null）、领取/释放提示及历史原因显示权。服务逐字段投影，不把领域返回的其它字段、员工账号、密码或全店审计带出去。
- `assertClaim/assertRelease(tx,actor,task)`在完整锁内确认真实处理/安全交接条件；需要的领域交接记录必须同事务保存，不能在提交后异步补写或发送外部请求。

通用读取范围始终同时满足“真实业务读取权”及“当前完整处理资格、当前/历史经办、或管理员协调范围之一”。管理员任务能力、旧经办记录都不能替代当前业务读取权；失去处理资格但仍保留业务读取权的原经办，可查必要历史且不能再领取。无权详情/历史与不存在统一404 TASK_NOT_FOUND。

资格同时检查固定目录全部依赖和任务保存的全部权限快照，支持未来同轮增加退款重试资格；不通过删减快照或未知权限放行，不自动给员工增权。allowedActions当前仅claim/release，供UI提示，提交仍重查。暂停/终结任务没有领取/释放动作。

生产业务和读取/交接注册表仍为空：列表/摘要返回真实空范围，任意UUID的孤立任务不展示或开放操作；内部阶段进入缺接入仍409 BUSINESS_MODULE_NOT_READY。所有成功业务场景来自专属SQL夹具，未向开发库造业务或任务。

### 查询快照、逾期与时间线

列表、总数、摘要、详情及时间线均在RepeatableRead事务内重新认证、读取当前权限和范围，不跨请求缓存身份或授权。列表总数和本页不会混用新增/删除前后的快照。

当前逾期=OPEN/CLAIMED/SUSPENDED且dueAt非空、now>=dueAt；终结任务不算当前逾期。历史曾逾期=持久everOverdue或当前已经到期，因此扫描尚未落事实时也如实显示。查询不写逾期事件、不伪装成扫描器；摘要currentOverdue/everOverdue按当前可读任务范围统计，可与本人待办/岗位池重叠，返回countsOverlap=true和asOf。

统一时间线对TaskHistory和DeadlineEvent先合并再分页，按occurredAt而非detectedAt排序；同一时间kind/id稳定。历史原因由真实领域授权，不允许显示时为null；只显示任务动作/经办变更及期限事实，不返回全店AuditLog、员工登录账号、凭证或内部请求信息。详情规则只投影阶段内核的9个固定快照键，最近期限事件沿用相同原因裁剪。

### 完整锁、版本与回滚

新增TaskLockService，复用第五步的员工及完整领域锁计划，阶段进入改为调用该服务，原34项集成回归通过。每次领取/释放尝试先只读定位任务、全部相关经办与上游对象，然后按全部员工ID→完整业务层级→Cursor→Task顺序取锁；候选关系或经办变化就整笔退出，不补逆序锁。

复用runAuthTransaction，增加可选领域重试判定：Task只额外重试TASK_LOCK_PLAN_CHANGED，与死锁/序列化冲突共用总计最多3次的整个事务上限。原认证调用不传判定时行为不变，版本冲突、业务拒绝、连接故障和超时不重试。第五步的内部阶段进入本身仍不自动开事务或重试，不能混为一谈。

锁后再次认证会话、当前岗位/权限/停用/强改密、业务读取范围及任务版本；真实领域检查等待后，写前再认证/授权。领取OPEN→CLAIMED、经办为本人、清reassignNeeded；释放CLAIMED→OPEN、清经办，必须领域确认安全交接，否则409 TASK_RELEASE_BLOCKED。两者版本+1，保留round、起算、规则和所有截止，不把释放变成阶段重入。

幂等使用动作+原expectedVersion作为服务端commandKey。只在任务仍为上次动作的结果、version=expectedVersion+1、历史主体一致，且释放原因规范化后一致时返回changed=false；不重复历史/审计。释放后再领取，或发生其它版本变化，旧请求不能ABA重放；他人已领取409 TASK_ALREADY_CLAIMED，非经办释放409 TASK_NOT_ASSIGNEE。版本达到数据库整数上限明确拒绝，不溢出。

Task、真实领域交接、TaskHistory和AuditLog同事务。新增task.claim/task.release最小审计，字段为前后任务状态、经办ID、轮次和任务版本；两动作只接受EMPLOYEE，SYSTEM原四项任务动作白名单明确列出，不随新增动作自动扩大。

### 本步边界与下一步

OpenAPI由32增至38操作，生成JSON调用器由30增至36；移除精确新增六条路径后，整个OpenAPI字节摘要与步骤6基线一致，旧32操作未改。没有新迁移、依赖、必要环境变量、开发演示账号或密码变更；未修改已应用0004。

当前任务HTTP已可用，任务页面、管理员转交/指派、员工资格同步回池、延期、统一扫描、BR-05及真实领域流程尚未完成。下一步拟做管理员转交/指派和员工资格变化同事务回池，修改任务命令、员工事务接入、审计及生成契约，重点验证目标资格、锁序、撤权/领取竞争、多任务回池与整体回滚；收到下一次“执行”后再推进。

## 步骤7：管理员转交与员工资格同步回池

### 指派和转交

新增`POST /admin/tasks/:id/transfer`，输入只有targetEmployeeId、expectedVersion、reason；原因规范化并限制1～500个Unicode码点，版本须原生非负整数。只允许当前SUPER_ADMIN且具备task.transfer，管理员自己接手也走同一套完整资格和领域条件校验。

OPEN可指派、CLAIMED可安全转交，SUSPENDED/COMPLETED/CANCELLED不能通过转交恢复；当前已是目标经办的同版本命令明确拒绝，避免制造无意义历史。目标须存在、ACTIVE、已改密且满足阶段目录、依赖和任务快照全部资格，缺失/不合资格统一409 TARGET_NOT_ELIGIBLE。不存在或不可读的任务仍404，管理员仍须真实业务读取权。

按全部员工ID升序→完整上游业务→Cursor→Task取锁，锁后核对操作者、经办集合、版本和目标资格，真实领域交接后再次核对操作者及读取范围。成功将任务设CLAIMED、经办设目标、清reassignNeeded、version+1；round、起算、规则、原截止/现截止及既有逾期事实保留。新增TRANSFERRED历史和task.transfer最小审计，真实操作者、requestId、原因、前后经办/状态/版本同事务。

只重放“同操作者、原expectedVersion、同目标、同规范化原因”的最后成功结果，且当前仍是version=expectedVersion+1的该目标CLAIMED任务，才changed=false；不重复领域同步、历史或审计。转交后再释放/领取、转回他人、换原因或旧版本均不能借幂等覆盖新结果。

### 真实领域交接端口

注册表增加独立`TaskBusinessHandoff`，通过`registerHandoff`注册；缺失、不完整或重复注册拒绝。`transfer(tx,actor,target,task)`必须确认真实业务可安全交接、目标具备该业务处理范围，并在原事务同步领域经办。`qualificationLost(tx,actorId,task,reason)`同步解除失资格经办，保留已完成业务事实、交运未决/核实阶段等真实状态；不得通过普通释放安全条件阻止撤权，也不能把交运未知改成普通待发货。两方法不在事务外补写或调用外部服务，领域故障必须向上抛出。

领域describe可给canTransfer只读提示；只有已注册交接端口、管理员合权限、任务OPEN/CLAIMED且版本未耗尽才显示transfer动作。提交仍执行完整规则，提示不替代校验。旧业务只注册领取/释放端口时不会突然显示转交；生产三类注册表仍为空，不提供默认成功实现。

### 员工原事务的两阶段接入

EmployeeEligibilityModule导入TasksModule，现有EmployeeEligibilityService从占位变为真实包装，TaskEligibilityService只导出内部事务端口。启停、调岗、额外授权三条员工命令沿用各自管理员稳定锁规则和操作者/目标员工ID升序锁，不新增事务后事件，也不把密码重置扩大为本轮回池触发器。

1. 员工身份/版本/差异检查后、任何员工写入前，prepare读取目标全部CLAIMED任务，按拟生效权限挑出失资格任务，合并所有涉及业务的完整上游计划。锁完全部顾客、订单、商品、SKU/库存、来源和业务附属记录后，依次锁全部Cursor、全部Task，同层ID升序；不逐单交错上游和下游，不补锁同业务其它员工。目标员工锁阻止新领取/转入，候选或上游计划变化须抛TASK_LOCK_PLAN_CHANGED，整笔回滚重定位。
2. 等待业务锁后、员工写入前重新认证操作者和当前命令权限；因此过期凭证不能提交变更，同时合法自停用/自降权不会被自己的新状态误拒绝。准备上下文用WeakMap绑定当前tx、目标、权限和真实操作信息，不能伪造、跨事务或重复消费。
3. 原员工状态/岗位/授权、版本、会话撤销和员工审计照常执行，再消费上下文同步回池：CLAIMED→OPEN、assignee=null、reassignNeeded=true、version+1；保留轮次、规则和期限。写QUALIFICATION_LOST历史及task.qualification.lost审计，actor为真实员工、requestId与员工命令相同，禁止SYSTEM冒名。

仍合资格的任务不改，无CLAIMED任务不造事件，终结任务不复活，重新启用不自动领回任务。岗位默认权限和个人授权按现有权威计算，不为满足任务而补权。任一领域同步、任务历史或审计失败，员工/授权/版本/会话及前面已处理任务一并回滚。锁集合变化、死锁及序列化冲突共用最多3次整笔尝试；业务拒绝、超时和版本上限不盲目重试。AuthSessionService重复取得已经持有的目标员工锁只为复用既有会话能力，不引入新的逆序资源。

### 契约、证据与后续

## 步骤8：管理员任务延期与期限事件

### 接口与文件职责

截止只接受`YYYY-MM-DDTHH:mm:ss(.1～3位毫秒)?Z`，秒级及短毫秒统一为`.sssZ`再比较；拒绝隐式本地时区、`+08:00`、2月30日、24点、闰秒和超过毫秒精度。新截止必须严格晚于服务器现在及已有截止，等号拒绝；原因沿用去首尾空白、Unicode码点1～500，版本为原生非负整数。未知字段仍400，不能夹带originalDueAt、状态、经办或轮次。

### 领域期限端口与事务

真实模块在启动时`registerDeadline(type,port)`，必须已注册真实业务；重复、不完整注册直接失败。`assertCanExtend(tx,actor,task)`只读验证真实阶段、计时类型和可延期条件；`extend(tx,actor,task,newDueAt)`在同一事务同步真实领域截止，不得事务外补写或发外部请求。传入截止为独立Date副本。外部等待类计时必须同步领域截止；付款截止、售后新申请窗口、自动收货基础计时和交运事实不能借本接口修改。

终结任务统一409 TASK_DEADLINE_BLOCKED。SUSPENDED是否允许由真实领域端口明确决定；延期本身保留暂停、经办和当前阶段，不恢复计时、不重新分派。读取端口可给`canExtendDeadline`只读提示，且已注册期限端口、管理员权限及活跃任务/可用版本同时满足才出现`allowedActions: extendDeadline`；提交仍重查全部条件。

每次尝试沿用全部员工ID升序→完整业务上游→Cursor→Task锁序。锁计划或经办集合变化整笔退出重定位，不逆序补锁；领域变化、死锁及序列化冲突共用最多3次尝试，版本冲突和业务拒绝不盲重试。持锁后、领域只读检查后、领域写入后均重新认证和核对当前业务范围；最终任务写入前再读服务器时钟，等待跨截止或凭证过期不能提交非法新期限。

### 旧逾期、首次指定与幂等

- 已有截止：写EXTENDED；deadlineAt保存本次被替换的旧截止，newDueAt保存新截止。originalDueAt、startedAt、规则/设置快照、轮次、状态、经办均保持，任务版本+1。
- 原来无截止：写DEADLINE_ASSIGNED，deadlineAt/newDueAt均为新截止；originalDueAt继续null，不把人工首次指定冒充原始SLA，不重算规则快照。
- 旧截止已到（`now>=dueAt`）先补OVERDUE：occurredAt为真实旧截止，detectedAt为本次最终服务器时刻；同任务同截止由既有部分唯一索引去重，保留更早firstOverdueAt和everOverdue。即使扫描没执行也不能抹掉曾逾期事实；多次延期的不同截止分别留事件。
- 公共逾期服务不另开事务、不自行取锁。旧顾客驱动事件仍记SYSTEM，AuditLog保留真实顾客主体；没有放宽SYSTEM旧审计动作白名单。
- 每次实际延期追加DEADLINE_CHANGED历史、`task.deadline.extend`审计，审计仅含前后dueAt/taskStatus/round/taskVersion及必填原因、真实员工和requestId。领域、补逾期、Task、期限事件、历史及审计任一点失败全部回滚。
- 动作键为原expectedVersion。同主体、同原版本、同规范化原因/UTC截止，且任务仍为version=expected+1和该截止时返回changed=false；仍认证并执行领域只读允许检查，不重复领域同步/事实/历史/审计。成功后新截止已到也可无写重放；另一主体、换原因、换截止或其它版本变化不能冒充该结果。

### 生命周期与共享事务

TaskEntryService新增inContext，向内核提供当前tx、真实主体、requestId、已锁员工集合和最终revalidate；上下文继续由withContext签发，只在回调中有效，不能伪造、跨业务或回调结束后复用。

生命周期要求真实领域注册assertTransition和applyTransition：前者核对当前业务允许条件，后者在原事务同步经办与真实状态。员工完成必须是当前经办，且满足固定阶段、权限依赖和任务附加快照全部资格；SYSTEM/顾客完成OPEN必须由真实领域明确允许，不能借管理员身份跳过领取规则。SUSPENDED不能直接完成，包括旧阶段替换入口；先合法恢复或取消旧轮。

暂停清经办，恢复到OPEN/null；保留round、startedAt、originalDueAt、dueAt、规则及设置快照。实际变更版本+1，必要时补旧逾期，再追加TaskHistory和受限审计；任一步失败与领域写入一并回滚。终结任务不复活，版本耗尽明确拒绝。注册了来源仓储时，仍有ACTIVE来源不得通过生命周期或阶段替换提前终结共享任务。

幂等核对命令键、原版本、真实主体、规范化原因和当前结果；只有相同成功结果可无写重放。顾客派生TaskHistory仍为SYSTEM，但另查对应AuditLog的真实主体和动作，避免SYSTEM或另一顾客借同一历史重放。领域校验和写入等待后再次认证；凭证到期不得提交。

后续领域须在任何领域锁之前进入withContext，先合并完整员工及上游锁计划；回调内执行领域写入、来源/计时/生命周期命令，错误传到最外层使整笔事务回滚。批量业务不得逐单交错上游和任务锁，也不得在已持下游锁后反向补锁员工或业务记录。

### 多来源共用阶段任务

来源固定为AFTER_SALE、SHIPMENT_EXCEPTION、STOCK_EXCEPTION、HANDOVER_UNCERTAIN、ADDRESS_REQUEST。真实来源仓储必须解析来源实体及其业务父对象，不能只验证浏览器传入UUID格式；提供assertSource/find/listActive/add/finish，并保存只追加来源历史、命令键、原因、真实主体、requestId和结束结果。

attach在已有有效同阶段任务时复用该Task；只有无有效任务时才经既有enterStage建立轮次。add/resolve/cancel都使用当前已锁事务。单个来源结束仅结束自己的关联；最后一个ACTIVE来源结束才按领域规则完成或取消任务，不提前结束其它异常。相同来源同命令重试不重复关联、历史或审计；换结束结果不能冒充重放，已终结来源不重新激活。并发结束在业务与任务锁下串行核对，来源与最后任务结束同事务。

### BR-05：阻塞与收货计时

OrderTimerService提供addBlock、releaseBlock、recordActualHandover、finishOrderTimer，要求ORDER完整锁上下文和真实仓储assertAllowed/load/save；save负责按版本保存订单、阻塞、周期、命令回执和领域历史。服务不另开事务，保存后重新认证并写最小审计，真实业务未接入时拒绝。

- 真实交运时刻加设置快照中的自然日天数建立基础截止；未发货、交运未知不启动收货计时。补录按真实过去交运起算，不能按录入时刻给订单重新计时。
- 第一个有效阻塞冻结remainingMs=max(当前截止−服务器现在,0)，建立唯一ACTIVE暂停周期并清有效截止；后续阻塞只追加来源，不再冻结。部分解除不恢复。
- 最后阻塞解除时恢复截止为现在加max(冻结剩余时长,三自然日)，三自然日复用北京时间日历工具。再次暂停建立新周期；旧命令回执绑定真实主体和参数，重放不会再次延长或解除新周期。
- 阻塞中补录过去交运时，先计算真实基础截止，再按当前核实时刻冻结；基础截止已经过去时剩余为0。完成/退款终结周期，不恢复；已完成后退款可继续终结处理。
- 规则返回独立对象和Date，不修改输入；检查版本、有效状态、日期、设置范围和多个ACTIVE周期等损坏状态。测试手算为11月18日剩2天、19日加阻塞、20日部分解除、25日最后解除到28日，不修改主机时间。

### 页面行为

- 摘要显示服务器asOf及本人未完成、合资格待领、当前/历史逾期；只有超级管理员且有task.transfer才展示待安排入口。普通员工手写待安排地址也不请求管理员列表。

- 提交立即禁用确认/取消，控制器同一事件循环只发一次写入。409/404要求重读；网络失败/5xx视为结果不确定，不能直接重发。成功后刷新详情、历史并失效列表/摘要，旧登录的迟到响应不能覆盖新页面。
- 手机使用单列筛选和详情，宽表在自身区域滚动；沿用既有后台配色和组件，不引入依赖或独立视觉系统。
