# 板块14经营查询短基线

日期：2026-11-15（北京时间）。入口：`node scripts/module14-performance.mjs`。每次先构建当前API，再由既有integration runner创建、完整迁移本轮随机 `m414_<uuid>_test` 数据库；完成后只移除本次专属库。文件、上传目录、检查点和证据保留，不做批量删除。常用环境、账户密码和原卷未改。

日常`pnpm test:integration`默认只运行非性能数据库回归，不会隐含启动本文件的10万单压力或依赖旧dist。性能套件保留在runner明确名单白名单中，由上述独占入口先构建后显式调用；直接指定套件时调用者须自行完成构建并确保资源独占。`M414_PERFORMANCE_PLAN_ONLY=1`仅供明确的计划诊断，写出`performanceThresholdVerified=false`，不能作为压力验收通过证据。

本轮范围是板块14的10万订单/100并发查询短基线：10秒预热，30秒持续发起测量，等待在途请求结束，逐接口记录p50/p95/p99、状态/错误量、吞吐、连接池借用排队、SQL分类耗时及锁采样。列表目标p95≤500毫秒，未降低。它不替代板块15的2分钟预热、5分钟测量、三轮以及完整写入/备份恢复验收。

## 数据与测量方式

性能库直接构造符合既有约束/外键的关联数据，明确不是正式购买或真实资金端到端证据：1000顾客、1000SPU/1000SKU、10万订单及明细、9.5万成功模拟支付、1万售后/退款/尝试/任务（5000成功退款、5000失败），10万审计和订单引用，200条额外业务历史。订单分布：75000完成、5000退款完成、5000已发货、5000待支付、10000待发货；事件分布60天。净消费抽取有100笔完成订单、失败退款不倒扣的顾客。SQL造数仅供性能，正式业务真值由其它真实命令集成套件证明。

测量覆盖overview、30天趋势、热销、库存预警、顾客列表、顾客净消费、全店审计、精确订单业务号审计、订单业务历史。100个实际HTTP在途，含真实JWT Guard、事务内授权、DTO及生产查询，读后核对订单/支付/退款/审计/引用/任务/库存流水数量和资金合计无变化。SQL预算在20和100行分别采集实际pg语句次数，不用页面能打开代替查询数量。COUNT、业务号、趋势、净消费、预警及历史采集真实参数化生产SQL的 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`，证据不保存SQL参数或JWT。

最终测量使用编译API独立Node子进程，HTTP发起端在测试进程，避免共享事件循环。子进程只使用本轮隔离库、随机端口及本轮私有上传目录；结束后仅停止本次子进程。探针通过显式 `--import` 加载测试文件，只在该子进程记录固定类别/耗时/错误码，无生产HTTP开关。摘要记录真实池容量、原超时、CPU/内存、PG版本/设置、关键dist SHA256及构建证据。

优化前9058个请求产生34221条事务控制语句。只在Reporting.read将隔离级别与只读模式合并为回调首句`SET TRANSACTION READ ONLY, ISOLATION LEVEL REPEATABLE READ`，早于任何SELECT；省去Prisma单独设置隔离级别的一次往返。依据[PostgreSQL16事务模式文档](https://www.postgresql.org/docs/16/sql-set-transaction.html)，模式可逗号组合且隔离级别须首条数据语句前设置。真实PostgreSQL测试检查`current_setting`、拒绝零行UPDATE的25006错误、并发写入后的固定MVCC快照及连接恢复；查询预算阈值保持原值。两轮最终压力使用同一明确配置独占执行，均按原阈值通过。

计划对照每种设置执行三次，并逐行比较结果一致：默认趋势45.277～45.607ms、热销28.260～29.097ms；关闭并行后分别64.777～67.380、36.659～37.894ms，更慢；按日LATERAL趋势226～265ms，明显更慢。临时支付覆盖索引没有被原查询自然计划采用，没有新增0018；所有候选索引在隔离库事务回滚，没有强制planner。数据造完执行ANALYZE，没有人为先VACUUM；测量期间记录到autovacuum，维护状态明确保留在证据中。
